# 共享状态并发

## 何时使用

- 当线程需要访问互斥器所保护的共享数据时
- 访问或使用 `Mutex<T>` 内部数据时。
- 当在循环中试图把同一个 `counter` 锁的所有权移动到多个线程时。
- 当使用 `Rc<T>` 管理引用计数并需要在线程间共享时。
- 并发操作需要锁住两个资源，且存在两个线程各持一个锁的情况。

## 核心原则

**使用互斥器所保护的数据之前要先尝试获取锁；处理完被互斥器所保护的数据之后必须解锁数据，这样其他线程才能获取锁。**

这样其他线程才能够获取锁。

**使用 `Mutex<T>` 内部数据前必须获取锁。**

`Mutex<i32>` 并不是 `i32`，类型系统不允许直接访问内部的 `i32` 值。

**不能将 `counter` 锁的所有权移动到多个线程中。**

错误信息表明 `counter` 值在上一次循环中被移动了，因此 Rust 告知不能将该锁所有权移动到多个线程中。

**`Rc<T>` 不能安全地在线程间共享。**

`Rc<T>` 管理引用计数时没有使用并发原语，改变计数的操作可能被其他线程打断，导致计数出错，进而可能造成内存泄漏或在值使用结束之前丢弃。

**当一个操作需要锁住两个资源，而两个线程各持一个锁时，会发生死锁并造成它们永远相互等待。**

Rust 不能避免使用 `Mutex<T>` 的全部逻辑错误；与 `Rc<T>` 可能造成引用循环类似，`Mutex<T>` 也有造成死锁的风险。

## 实践模式

**共享内存并发**

共享内存类似于多所有权：多个线程可以同时访问相同的内存位置。

- 互斥器

**MutexGuard**

`lock` 调用返回的智能指针，它实现 `Deref` 指向内部数据，并在离开作用域时通过 `Drop` 自动释放锁。

- 示例 16-12 中，`MutexGuard` 在内部作用域结尾自动释放锁。

**Arc<T>**

Arc<T> 是一个类似 Rc<T> 并可以安全用于并发环境的原子引用计数类型；其原子性类型工作起来类似原始类型，但可以安全在线程间共享。

- Arc<T> 与 Rc<T> 有着相同的 API，修改程序中的 use 行和 new 调用即可切换到 Arc<T>，示例 16-15 中的代码最终可以编译和运行。

**Mutex<T> 的内部可变性**

当 `counter` 不可变时，可以获取其内部值的可变引用；`Mutex<T>` 提供了这种内部可变性，就像 `Cell` 系列类型那样。

- 正如第 15 章中使用 `RefCell<T>` 可以改变 `Rc<T>` 中的内容那样，使用 `Mutex<T>` 可以改变 `Arc<T>` 中的内容。

## 常见陷阱

- **在共享麦克风使用中，成员结束发言后忘记将麦克风交还。**
  - 后果：其他人将无法发言；如果对共享麦克风的管理出现问题，座谈会将无法如期进行。
  - 纠正：发言结束后将麦克风交给下一位希望讲话的成员。
- **使用 `Mutex<T>` 时在多个线程中同时锁定多个资源，且各线程持有一个锁并等待另一个。**
  - 后果：死锁，线程永远相互等待。
  - 纠正：避免同时持有多个锁，或者设计一致的锁顺序；研究并使用死锁规避策略。
