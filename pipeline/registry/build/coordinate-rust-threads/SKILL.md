# 用线程、通道与 Arc<Mutex> 协调并发

## 何时使用

- 把耗时任并行执行、需要收集结果时
- 在「用通道传递数据」与「用共享状态」之间选型时
- 多线程共享计数器/缓存/注册表、借用检查器报 Send/Sync 错误时
- 排查死锁、线程未收敛、锁持有过久等并发问题

## 输入与前置条件

- 任务清单与数据依赖（哪些数据要跨线程流动）
- 并发风格倾向（消息传递或共享状态）
- 共享资源的访问模式（读多写少、更新语义）

## 执行步骤

1. 划分并发单元：确定每个线程要处理的任务与其数据归属。
2. spawn 线程并移交所有权：闭包加 move 转移捕获值；核对移交后主线程不再使用这些值。
3. 用 JoinHandle 与 join 汇总：保证所有线程都有等待点，不遗漏收尾（调度顺序不保证，结果收集与顺序无关）。
4. 选择通信或共享：数据单向流动用 mpsc 通道（send 转移所有权、接收端可当迭代器、发送端丢弃即关闭）；多线程读写同一状态用 Arc<Mutex<T>>。
5. 共享状态细节：Rc 不能跨线程，改用 Arc；锁内只做必要操作，避免嵌套获取两把锁造成死锁；MutexGuard 离开作用域自动解锁。
6. 在锁边界上设计数据所有权：把「先取锁再算」改为「先算好再短临界区更新」。

## 交付物

- 并发结构（线程划分、通道或共享状态拓扑）
- 所有权与 move 决策说明
- 锁粒度与死锁防护说明

## 检查、停止与回滚

- 全部 JoinHandle 都被 join（或有意分离并说明）
- 跨线程数据无 Rc 残留；共享可变数据使用 Arc<Mutex>（或说明替代方案）
- 不存在嵌套上锁路径（或已评估锁顺序可避免死锁）
- 通道发送端关闭语义与接收端退出条件一致，无永久阻塞
- 停止条件：出现需要跨线程的可变共享但性能要求排除锁方案时，暂停并评估替代并发模型（超出本任务范围）
- 停止条件：死锁已复现但无法定位锁序问题时，先补最小复现再继续
- 回滚：已定义。保留修改前并发结构；回滚即恢复原实现并重新跑并发用例。

## 依据与边界

**来源规则**

- Rust 标准库只提供 1:1 线程模型实现。
- 多个线程可能轮流运行，但并不保证如此；实际调度顺序依赖操作系统如何调度线程。
- 保存 thread::spawn 返回的 JoinHandle 并调用其 join 方法，能确保新建线程在 main 退出前结束运行。
- 当 Rust 默认保守地只为线程借用主线程数据时，应通过 `move` 关键字将值的所有权移动到新建线程，向 Rust 保证主线程不会再使用该值；`move` 关键字覆盖 Rust 默认保守的借用，但不允许违反所有权规则。
- `send` 函数获取其参数的所有权并移动这个值归接收者所有；这可以防止在发送后再次意外地使用这个值。
- 通道接收端 rx 可以被当作迭代器使用；当通道关闭时，迭代器结束。
- 使用互斥器所保护的数据之前要先尝试获取锁；处理完被互斥器所保护的数据之后必须解锁数据，这样其他线程才能获取锁。
- 使用 `Mutex<T>` 内部数据前必须获取锁。
- 不能将 `counter` 锁的所有权移动到多个线程中。
- `Rc<T>` 不能安全地在线程间共享。
- 当一个操作需要锁住两个资源，而两个线程各持一个锁时，会发生死锁并造成它们永远相互等待。

**来源陷阱**

- 在共享麦克风使用中，成员结束发言后忘记将麦克风交还。
  - 后果：其他人将无法发言；如果对共享麦克风的管理出现问题，座谈会将无法如期进行。
  - 纠正：发言结束后将麦克风交给下一位希望讲话的成员。
- 创建线程后不保存 `thread::spawn` 返回的 `JoinHandle`，也从不调用 `join` 等待线程完成。
  - 后果：主线程结束时新建线程会被提前终止，甚至可能完全没有被执行；线程是否运行和运行到哪里取决于调度，无法保证。
  - 纠正：将 `thread::spawn` 的返回值存入变量，并在合适位置调用 `join` 方法阻塞当前线程，直到该线程执行完毕。
- 在 `thread::spawn` 的闭包中借用主线程的局部变量，却不同时使用 `move` 取得其所有权。
  - 后果：新线程可能被调度到后台尚未执行，而主线程已经丢弃该值，使线程中的引用在执行时无效。
  - 纠正：对闭包使用 `move` 强制获取所用值的所有权，将值从主线程移动到新线程，避免借用失效。
- 在 `thread::spawn` 闭包中直接使用主线程数据而没有使用 `move`，依赖编译器的默认借用捕获。
  - 后果：闭包只借用主线程数据，而新线程执行时长未知，引用可能在主线程 drop 后失效，导致编译错误或潜在悬垂。
  - 纠正：需要把数据所有权转移到新线程时，在闭包前加 `move` 关键字；注意 move 后主线程不能再使用该值。
- 在值被移动（赋值给其他变量、插入哈希 map、发送到通道、移入拥有所有权的数据结构）之后，继续访问或使用原始绑定。
  - 后果：编译器会以 `use of moved value`（E0382）拒绝代码，防止潜在的双重释放、无效变量以及并发线程对已发送值的后续修改或丢弃导致的数据不一致。
  - 纠正：移动后不再使用原绑定；如果多个位置需要共享同一数据，在单线程场景改用 `Rc<T>` 的引用计数共享，并用 `Rc::clone` 增加计数，而不是将所有权移入单一所有者。
- 通过通道 `send` 将值发送给另一个线程后，还在当前线程继续读取或使用该值。
  - 后果：接收线程可能先修改或丢弃该值，导致当前线程读到不一致或不存在的数据，产生错误或意外结果。
  - 纠正：接受 `send` 的所有权转移语义：发送后不再使用该值。如果确实需要保留，应在发送前克隆出独立副本。
- 使用 `Mutex<T>` 时在多个线程中同时锁定多个资源，且各线程持有一个锁并等待另一个。
  - 后果：死锁，线程永远相互等待。
  - 纠正：避免同时持有多个锁，或者设计一致的锁顺序；研究并使用死锁规避策略。

**适用边界**

- 不覆盖无锁数据结构与原子类型的高级用法
- 不覆盖 async/await 任务调度（不同运行时模型）
- 不覆盖线程池与工作窃取实现
