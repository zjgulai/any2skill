# 用所有权安全地实现 Rust 状态模式

## 何时使用

- 把带状态的业务流程（发布、订单、连接协议）建模为状态机时
- 希望状态转换规则被类型系统与可见性约束保护时
- 状态需要持有数据并随转换整体转移时
- 对比「trait 对象状态模式」与「枚举+match」两条路线的取舍时

## 输入与前置条件

- 状态清单与合法转换（含非法转换的期望行为）
- 每个状态携带的数据
- 对外暴露的接口（哪些操作在各状态下可用）

## 执行步骤

1. 开工前抄录任务的字面要求清单（文件名、命名、签名、输出格式与指定片段），实现与说明以该清单为准；技能用于判断与结构，不用于改写任务指定的表面形式。
2. 定义 State trait：为每个状态实现统一的行为接口（如请求处理、发布尝试），非法操作返回错误而不是静默忽略。
3. 把状态字段设为私有：外部代码只能经方法触发转换，无法直接改写状态。
4. 用 Box<dyn State> 存储当前状态：trait 对象允许运行期替换具体状态。
5. 实现状态转移时解决所有权搬迁：字段用 Option<Box<dyn State>> 包裹，用 take 取出旧状态、消费后写入新状态，避免同时借用与移动。
6. 只读访问状态时用 as_ref 取引用，不触发移动。
7. 对照枚举+match 路线做取舍：trait 对象路线新增状态不动既有状态代码、但增加行为扩展成本；枚举路线穷举分发、但新增状态需改动所有 match 点。

## 交付物

- State trait 与各状态实现
- 上下文类型（私有状态字段、Option+take 转移）
- 两条路线的取舍记录

## 检查、停止与回滚

- 任务给定的命名与输出格式逐字保留（与字面要求清单逐项核对）。
- 状态字段不可被外部直接修改（私有性生效）
- 转移路径中无同时借用与移动（编译通过，take/as_ref 使用正确）
- 非法转换返回显式错误而非静默保持原状态
- 取舍记录涵盖「新增状态需要改哪些文件」的实际成本
- 停止条件：状态数量多且转换矩阵复杂到 trait 路线维护成本明显过高时，暂停并评估改用枚举路线
- 停止条件：需要跨线程共享状态机时转 coordinate-rust-threads 处理同步
- 回滚：已定义。保留改造前实现；回滚即恢复原结构并复跑状态转换用例。

## 依据与边界

**来源规则**

- Post 的 `state` 字段是私有的，因而无法创建任何其他状态的 `Post` 实例。
- 创建新 `Post` 时，`state` 字段必须设置为一个存放了 `Box` 的 `Some` 值，且该 `Box` 指向 `Draft` 结构体新实例，以确保从草案开始。
- 当博文仅处于草案状态时，`content` 方法应总是返回空字符串 slice。
- 在 Rust 状态模式中需要取得状态字段所有权时，将状态字段包装为 Option，并调用 take 取出其中的 Some 值、留下 None，从而把旧状态移出 Post 而不是借用它。
- 在 `&self` 方法中需要 `Option<Box<State>>` 中值的引用时，应调用 `as_ref` 获得引用，而不是移动 `state`。
- 发布博文工作流的规则逻辑应存在于状态对象中，而不是分散在 `Post` 中。
- 在状态模式中，由于状态之间相互联系，当需要在两个已有状态之间插入新状态时，必须修改负责转换到新状态的已有状态代码。
- 草案博文应完全没有 `content` 方法；这样尝试获取草案博文内容会得到方法不存在的编译错误，并使生产环境不可能意外显示草案博文内容。

**来源陷阱**

- 完全按照面向对象语言的定义实现状态模式
  - 后果：没有尽可能地利用 Rust 的优势
  - 纠正：进行代码修改，将无效的状态和状态转移变为编译时错误

**适用边界**

- 技能术语与任务字面冲突时，以任务字面为准。
- 不覆盖持久化状态机的存储与恢复
- 不覆盖分布式状态同步
- 枚举替代方案的完整论证超出本任务范围，只做取舍要点
