# 压缩上下文并维持运行状态

## 何时使用

- Agent 在长任务中丢失关键信息或反复纠结已解决的问题时
- 为框架设计上下文压缩、状态栏或运行进度注入时
- 缓存命中率异常、怀疑状态更新方式反复重建前缀时
- 需要控制长轨迹的 token 成本、给 Agent 注入预算与进度信息时

## 输入与前置条件

- 当前上下文构造方式（静态前缀与动态历史的划分）
- 上下文窗口大小与典型使用率
- 需要跨轮次维持的状态清单（进度、计数、环境摘要）

## 执行步骤

1. 定义状态栏内容与注入位置：作为 user 角色消息附在动态历史末尾，不修改系统提示词前缀。
2. 实现计数类元信息（如工具调用次数）在工具结果内直接回显，让模型无需自己归纳。
3. 设定压缩触发：持续监控上下文使用率，达到阈值（如 80%）时激活压缩管线。
4. 压缩只发生在两次模型调用之间，只处理工具结果等低价值段；低价值噪声直接删除，不做摘要。
5. 维护「不可丢」清单（时间、实体名、结论与约束）并在压缩后用抽检验证保全。
6. 按轨迹长度与状态大小选择状态更新实现：小状态长会话可保留旧状态重算短后缀，大状态高频更新则截断重写。
7. 可选：把总预算与剩余预算注入提示词，按剩余预算调整探索与利用的权重。

## 交付物

- 状态栏规范（内容、注入位置、格式）
- 压缩管线设计（触发条件、处理范围、保全清单）
- 状态更新实现选型说明（含缓存代价权衡）

## 检查、停止与回滚

- 压缩后系统提示词前缀逐字节不变，缓存前缀得以保留
- 抽检压缩结果：「不可丢」清单中的关键信息全部仍在
- 状态栏计数与实际工具调用次数一致
- 压缩不在两次调用之间以外发生，也不把摘要当作删除低价值内容的替代
- 停止条件：压缩后复检发现关键信息丢失且无法恢复时停止并回退到压缩前状态
- 停止条件：上下文使用率持续超过窗口且压缩无法降下时，暂停任务并交由人工决定拆解
- 回滚：已定义。压缩前的消息列表应可恢复（工具摘要是可重建的派生数据）；回滚即恢复压缩前历史并重新规划压缩时机。

## 依据与边界

**来源规则**

- 当需要理解为什么 Agent 状态栏在长上下文中有效时
- 在 Agent 需要打电话处理业务且系统提示词要求拨打每个商家不超过 3 次的场景中，在每次电话工具的调用结果中直接标明累计呼叫次数（如“本次是第 3 次呼叫该商家”），能让模型立即发现已达到限制，不再继续呼叫，错误率大幅降低。
- Agent 状态栏在 API 层面作为一条 user 角色的消息插入到上下文末尾，而不是修改开头的 system 消息。
- 当状态很小、两次更新间产生的消息很多，且会话长度受控时：选择持久追加（实现二）；当状态较大、更新频繁或轨迹很长时：选择每轮替换（实现一）；当当 αSN/2 < (1-α)R 时：倾向实现二，否则倾向实现一
- 需要维护 Agent 状态栏中的数量统计或元信息时——建议：优先用代码维护状态栏；必须使用 LLM 时，只让它逐条抽取、由代码汇总，不要让它一次性批量统计。
- 进行上下文压缩时，不要让模型被动地在海量信息中检索，而要主动为模型提供经过提炼的结构化知识。
- 上下文压缩应发生在两次 API 调用之间，由 Agent 框架对消息列表进行预处理；System Prompt 和 Tool Definitions 永远不动，压缩的对象是对话历史中的 tool results。
- 自适应窗口化策略通过持续监控上下文使用率，在 prompt token 数超过窗口的 80% 时激活压缩；触发后一次性压缩所有未标记的工具结果，并添加 [COMPRESSED] 标记防止已压缩内容被重复处理。
- 低价值噪声内容应直接移除，不做摘要。
- API 层微压缩适合在上下文即将溢出、反正要付出缓存重建代价时使用，而不应频繁触发。
- 压缩时不得丢失关键信息，例如时间和公司名

**来源陷阱**

- 把所有原始信息堆在上下文里。
  - 后果：模型每次决策都要在数万 token 中反复检索相关片段，注意力被分散，关键信息容易被遗漏。
  - 纠正：先用一次 LLM 调用把已有信息结构化总结成“目前已知：A 是……，B 是……，还缺 C 的信息”，后续思考直接使用这份精炼表示。
- 当模型认为上下文窗口即将耗尽时，可能在任务尚未完成前提前收尾。
  - 后果：任务尚未完成前提前收尾。
  - 纠正：在上下文窗口尚未接近耗尽时就提前压缩，可能提升模型的决策质量。
- 把所有信息零散地放在 Agent 执行历史中，而不是定期记录到文档
  - 后果：早期架构决策、约束背后的理由和失败路径容易丢失
  - 纠正：Agent 定期将进展记录到文档中；若模型没有文档化习惯，通过 prompt 和 skill 提醒它

**适用边界**

- 不含子 Agent 委派与任务隔离（见 coordinate-agent-work）
- 不含多 Agent 共享状态的一致性（见 coordinate-agent-work）
- 要适配具体推理服务的 KV 缓存实现时，需按该服务文档核实前缀规则
