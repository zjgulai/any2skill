# 工具设计的通用原则

## 何时使用

- 当设计面向 Agent 使用的工具时。
- 当确实需要专用工具，且多个工具在功能相似性或使用场景上存在重叠时。
- 当确实需要对输入进行规范化处理（如统一编码格式）时，必须在工具描述中加以说明，并在工具返回中明确告知模型。
- 当工具描述缺少反例说明、LLM 可能自行猜测时
- 当 Agent 频繁选错工具时

## 核心原则

**工具应该对应 Agent 的目标，而不是底层的 API 操作。**

把每个 API 端点包成一个工具会导致粒度过细，Agent 往往要协调好几个工具才能完成一个目标。

**即使确实需要专用工具，粒度也应偏向整合而非细分。**

粒度过细会导致工具数量激增，增加 LLM 的选择负担；根据功能相似性和使用场景重叠度整合工具，可以降低认知负担、使描述更清晰并便于扩展。

**工具的参数传递必须保持透明，不得在模型不知情的情况下修改输入或输出。**

模型感知到的世界与工具操作的世界之间不能存在系统性偏差；否则工具的“智能修正”会制造模型无法自行诊断的系统性故障。

## 实践模式

**Skill**

Skill 是用自然语言编写的操作流程文档，Agent 通过终端或代码解释器逐步执行；它只需少量通用工具即可覆盖大量场景，目录条目只占几十个 token，正文用到时才读取。

- 部署应用 Skill 文档：1. 运行 npm run build 构建项目；2. 运行 docker build -t app:latest . 打包镜像；3. 运行 kubectl apply -f deploy.yaml 部署到集群，由 Agent 通过 bash 工具逐步执行。

**静默参数注入**

静默参数注入是一种保真性违规：工具在模型不知情的情况下向命令追加额外的参数。

- 某 IDE 的 bash 工具在执行所有 git commit 命令时自动附加一个额外参数，用于标记这次提交是由 AI 生成的。

## 常见陷阱

- **把每个 API 端点包成一个工具，粒度过细。**
  - 后果：Agent 往往要协调好几个工具才能完成一个目标。
  - 纠正：工具应该对应 Agent 的目标，而不是底层的 API 操作。
