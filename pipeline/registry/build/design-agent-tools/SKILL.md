# 设计可选、透明、可分页的 Agent 工具

## 何时使用

- 为 Agent 新增或重构工具接口时
- Agent 频繁选错工具或传错参数、需要从描述与返回格式找原因时
- 设计搜索类工具、需要决定结果格式与分页策略时
- 读取类工具内容超限、需要定义截断行为时
- 通过 MCP 或能力市场引入第三方工具、需要审查描述与凭证时

## 输入与前置条件

- 工具要服务的 Agent 目标（不是底层 API 端点清单）
- 调用场景与典型参数、预期返回规模
- 同类/重叠工具的现状清单
- 引入第三方能力时的来源、版本与凭证要求

## 执行步骤

1. 按 Agent 目标而不是 API 端点划分工具粒度；重叠工具按功能相似性与场景重叠度做整合。
2. 为每个工具写描述四要素：什么时候用、什么时候不用（边界与反例）、参数格式的具体示例（含单位与默认值）、1 到 5 个真实调用示例。
3. 设计返回：搜索类返回结构化候选（标题、位置、摘要片段）而不是拼接全文；结果多时提供游标或分页参数，并注明总数与翻页方式。
4. 定义截断行为：注明省略了多少内容、如何读取剩余部分；禁止静默截断。
5. 保持参数透明：不修改模型不知情的输入输出；确需规范化（如统一编码）时在描述中声明、在返回中告知。
6. 引入外部能力时审查描述与版本、隔离凭证，保证模型看到的参数与真实调用一致。
7. 能力表达形式选型：默认用通用工具；仅当安全权限、参数复杂、使用频率极高、平台差异四类情况下才封装专用工具。

## 交付物

- 工具清单：粒度决策与整合说明
- 每个工具的描述文本（四要素齐全）
- 返回格式与分页/截断规范
- 第三方能力引入审查记录

## 检查、停止与回滚

- 每个工具描述包含使用时机、不用场景与反例，参数有具体示例
- 搜索类返回包含结构化候选、总数与翻页方式
- 所有截断点有显式省略说明
- 不存在静默参数注入或静默输入转换
- 公共 API 或命令会产生同名遮蔽风险时已显式检测
- 停止条件：工具的预期行为与安全边界冲突（需要超出授权范围的能力）时停止并升级评审
- 停止条件：第三方描述无法核实或与实测行为不符时，暂停引入
- 回滚：已定义。工具描述与返回格式的变更应保留旧版本记录；回滚即恢复上一版描述/格式并对已发现的选错场景复跑。

## 依据与边界

**来源规则**

- 决定能力用什么形式表达时，应默认使用通用工具，只在安全权限、参数复杂、使用频率极高和平台差异这四种情况下退回专用工具。
- 感知工具的设计关键在于控制输出信息量，防止上下文爆炸。
- 执行工具的设计核心是安全约束。
- 工具应该对应 Agent 的目标，而不是底层的 API 操作。
- 即使确实需要专用工具，粒度也应偏向整合而非细分。
- 当工具描述缺少反例说明、LLM 可能自行猜测时——建议：清晰列出工具的边界条件——做不到什么、不接受什么输入，往往比描述能力本身更重要。
- 当 Agent 频繁选错工具时——建议：优先检查工具描述，而不是怀疑模型能力。
- 工具的参数传递必须保持透明，不得在模型不知情的情况下修改输入或输出。
- 搜索工具的返回值应为结构化候选列表（标题、位置、摘要片段），而不是拼接后的全文；当结果数量较多时，应提供分页或游标（cursor）参数，默认只返回前若干条，并在返回值中注明结果总数和获取下一页的方式，由 Agent 自主决定是否继续翻页，而不是一次性倾倒全部结果。
- 读取类工具在内容超过阈值必须截断时，应明确标示截断情况：注明省略了多少内容以及如何读取剩余部分；不得静默截断。
- 案例：实验 4-3 ★★：多模态信息提取：三种技术范式的对比分析——三种范式存在清晰权衡：原生多模态模式在分析图表、理解文档布局等任务上表现最佳；提取为文本模式在处理纯文本占主导的文档时成本效益最高，但完全无法处理需要视觉信息的查询；工具化模式在交互式场景中展现灵活性，能以较低成本处理大多数初步查询，但在需要一次性端到端深度理解的场景下表现不如原生模式。

**来源陷阱**

- 把每个 API 端点包成一个工具，粒度过细。
  - 后果：Agent 往往要协调好几个工具才能完成一个目标。
  - 纠正：工具应该对应 Agent 的目标，而不是底层的 API 操作。
- 工具描述只说明“能做什么”，不说明“什么时候用/不用”、不列出边界和反例，参数也只给抽象规范而非具体示例。
  - 后果：模型会自行猜测边界，导致工具选择错误、传参错误和输出解析错误；移除描述性文本的消融实验中工具调用错误率增加45%。
  - 纠正：为每个工具写清使用时机、边界条件（做不到什么、不接受什么输入），参数描述提供具体格式示例，并补充1-5个真实调用示例；当模型频繁选错工具时优先检查工具描述。
- 工具在参数传递层静默转换模型输入/输出，或静默注入额外参数，而不是保持透明。
  - 后果：模型看到的内容与实际操作不一致，反复尝试却总是失败，又无法根据可见信息诊断原因，陷入困惑。
  - 纠正：参数传递必须透明：不修改模型不知情的输入输出；若必须规范化（如统一编码），应在工具描述中声明并在返回中告知模型。

**适用边界**

- 不覆盖具体传输协议实现细节（HTTP、stdio 等按各自文档）
- 不覆盖执行工具内部的安全实现（见 secure-agent-actions）
- 不承诺为任意框架生成可直接落地的代码，产出以设计规格为主
