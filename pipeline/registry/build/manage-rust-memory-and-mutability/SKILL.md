# 管理 Rust 内存布局、析构与内部可变性

## 何时使用

- 定义递归类型（树、链表、状态机嵌套）报无限大小错误时
- 大对象需要转移所有权但不想深拷贝、考虑装箱时
- 资源（文件、连接、锁）需要确定的释放时序、或需要提前释放时
- 在 &self 方法里需要修改字段、借用检查阻止直接改时

## 输入与前置条件

- 类型定义与目标数据结构的形态（递归与否、是否共享）
- 资源生命周期与释放要求
- 可变性需求：单线程可变共享还是多线程
- 相关错误输出（如 E0072）

## 执行步骤

1. 递归类型报错时用 Box 断开无限大小：枚举变体或字段改为 Box<T>；核对枚举本身大小取最大成员。
2. 按三场景评估 Box：未知大小类型必须装箱；大数据转移装箱以获得固定大小的浅拷贝移动；需要 trait 对象时装箱。
3. 析构交由 Drop 自动完成：不要实现手动释放；需要提前释放时用 std::mem::drop（不能直接调用 .drop()）。
4. 确认析构时序与资源释放点；对锁等 RAII 资源核对离开作用域即释放。
5. 单线程内需要「外部不可变、内部可变」时用 RefCell：确认借用规则在运行时检查，违反即 panic（BorrowMutError）而非编译错误。
6. 需要多所有者共享可变数据时组合 Rc<RefCell<T>>；明确单线程限制。
7. 核对借用不重叠：RefCell 的 borrow/borrow_mut 作用域要短，避免在借用未结束时再次可变借用。

## 检查、停止与回滚

- 递归类型编译通过，E0072 消失
- 无直接调用 drop 方法的代码，提前释放统一走 std::mem::drop
- RefCell 的 borrow_mut 作用域内无其他活跃借用（无 panic 风险路径）
- Rc<RefCell<T>> 未跨线程使用；跨线程场景已改用线程安全组合
- 停止条件：可变共享出现跨线程需求时，暂停并转 coordinate-rust-threads
- 停止条件：RefCell 借用冲突在运行期反复出现、说明设计层面存在别名控制问题时，回到所有权设计而不是加 try_borrow 硬撑
- 回滚：已定义。保留修改前类型定义；回滚即恢复原结构并复编译验证。

## 依据与边界

**来源规则**

- 当只需要储存像单个 i32 这样的普通值时——建议：默认使用栈上储存，而不是使用 Box；避免单独使用 Box 存放一个值
- 在 Rust 中，像 `List` 这样的递归类型，如果其成员直接存放另一个相同类型的值，编译器会认为该类型有无限大小，且无法计算存储该类型值所需的空间。
- 对于非递归枚举类型，Rust 计算其值所需分配空间时，取存储其最大成员所需的空间大小。
- 所需功能仅为间接存储和堆分配，而不需要其他智能指针的特殊功能——建议：使用 Box<T>，因为它没有特殊功能带来的性能损失
- 当需要在值离开作用域之前强制清理值时，应使用 `std::mem::drop` 函数，而不能显式调用 `drop`。
- 当需要相同数据有多个所有者：选择 Rc<T>；当需要单一所有者，且希望在编译时执行不可变或可变借用检查：选择 Box<T>；当需要单一所有者，且希望在运行时执行不可变或可变借用检查，或需要在不可变值内部改变值：选择 RefCell<T>
- RefCell<T> 只能用于单线程场景。
- `RefCell<T>` 获得内部可变性时并没有完全绕开借用规则；编译器中的借用检查器允许内部可变性并相应地在运行时检查借用规则，违反这些规则会导致 panic 而不是编译错误。
- 当实现一个 trait 的方法时必须保持 `&self` 签名，而该方法又需要修改其内部字段时，应使用 `RefCell` 来存储该字段，以获得内部可变性并在不可变借用下修改内部值。
- `RefCell<T>` 在任何时候只允许有多个不可变借用或一个可变借用。
- 需要一个值有多个所有者，并且需要修改该值——建议：将 `RefCell<T>` 存储在 `Rc<T>` 中，以同时获得多个所有者和可变访问能力

**来源陷阱**

- 在递归类型中直接储存一个值，而不是间接地储存指向值的指针
  - 后果：编译器无法计算出要为递归类型分配多少空间，从而给出错误
  - 纠正：插入间接存储（例如 Box、Rc 或 &），使递归类型可表示
- 在其他一些语言中，每次使用完智能指针实例后必须手动调用清理内存或资源的代码。
  - 后果：如果忘记手动调用清理代码，运行代码的系统可能会因为负荷过重而崩溃。
  - 纠正：在 Rust 中指定每当值离开作用域时被执行的代码，由编译器自动插入这些代码，从而无需在程序中到处编写清理代码，也不会泄漏资源。
- 对不可变局部变量 `x` 进行可变借用（`let y = &mut x;`）
  - 后果：编译失败，编译器报错 E0596：不能将不可变局部变量 `x` 作为可变借用
  - 纠正：按编译器提示将 `x` 改为可变绑定 `mut x`
- 在同一作用域中连续调用 `borrow_mut` 创建两个可变借用。
  - 后果：违反 `RefCell<T>` 的运行时借用规则，代码能编译通过但测试失败。
  - 纠正：不要在相同作用域同时创建两个可变借用。
- 在定义递归类型（如 cons list）时直接存放相同类型的成员而不插入间接层。
  - 后果：编译器报错 recursive type `List` has infinite size，无法计算内存布局。
  - 纠正：在递归成员中插入 `Box<T>`（或 `Rc<T>`、引用）提供间接存储，使类型具有已知大小。
- 显式调用实现 `Drop` trait 值的 `drop` 方法。
  - 后果：编译错误 explicit destructor calls not allowed；如果允许会导致 double free。
  - 纠正：使用 `std::mem::drop` 函数在需要时提早丢弃值。
- 试图通过不可变引用修改其指向的内容，或在不可变变量上创建可变引用。
  - 后果：编译器拒绝编译，防止程序在不可变语义下意外改变数据。
  - 纠正：当确需修改值时，将变量声明为 `mut` 并使用 `&mut` 可变引用；若只想读取，则保持不可变引用。
- 在同一个作用域内同时持有对同一数据的多个可变引用，或在持有不可变引用的同时创建可变引用。
  - 后果：可能造成数据竞争或未定义行为，编译器以借用冲突错误拒绝代码，避免难以追踪的运行时并发/别名 bug。
  - 纠正：用大括号块将不同借用限制在不同作用域中，或让不可变引用的最后一次使用在可变引用创建之前结束（利用 NLL），保证同一时间只有一种借用存在。
- 在相同作用域内通过 `RefCell<T>` 创建两个活跃的可变借用（调用两次 `borrow_mut`）。
  - 后果：程序运行时 panic，出现 `BorrowMutError` 而不是编译错误。
  - 纠正：遵守借用规则，同一时间只允许一个可变借用或多个不可变借用，用作用域控制活动借用生命周期。
- 在 mock 对象中，当 trait 方法签名要求 `&self` 时，试图直接修改普通 `Vec` 等字段来记录调用，或把方法签名改成 `&mut self`。
  - 后果：产生借用检查错误（如 E0596），或改变 trait 实现签名导致不符合接口，mock 无法记录消息，测试无法断言行为。
  - 纠正：使用 `RefCell<T>` 包装需要修改的内部状态，在 `&self` 方法中通过 `borrow_mut` 修改、通过 `borrow` 读取，保持 trait 签名不变。

**适用边界**

- 不覆盖 Deref/DerefMut 强制转换的完整语义
- 不覆盖弱引用与循环引用的内存泄漏分析
- 不覆盖跨线程共享（见 coordinate-rust-threads）
