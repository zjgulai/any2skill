# 划清 Agent 边界并建立动作安全防线

## 何时使用

- 设计新 Agent 系统、需要先划清可观察与可执行的边界时
- 评审已有系统：某项能力缺失或失控，是提示、上下文还是工具层的问题
- 决定一个操作走通用工具还是封装专用工具时
- 上线前为 Agent 动作做安全评审、设计护栏分层与人工确认阈值时
- 外部内容（网页、邮件、工具结果、第三方技能）将进入上下文或长期记忆时

## 输入与前置条件

- 任务清单与期望能力（Agent 要完成什么）
- 现有或计划中的观察通道与动作接口、运行环境与权限约束
- 动作清单及其可逆性、权限、影响面
- 外部内容来源清单与数据层可用的真值来源（数据库、服务端时钟）

## 执行步骤

1. 列出观察通道与动作接口：逐项确认哪些信息真正进入上下文、哪些操作被允许；未进入/未开放的显式标记为不可见/做不到。
2. 把职责分到层（上下文构造、工具接口、循环与状态），并按整合理由做工具粒度决策；需要专用工具时按四类例外取舍。
3. 把安全护栏分成上下文层、执行层、数据层三层，逐层标注「能防什么、不能防什么」；不把黑名单当唯一机制。
4. 对外部内容统一打标并标注来源；按可逆性给动作分级——可逆走快路径，不可逆或高风险转慢路径或人工确认。
5. 把政策事实（金额、时间、状态、权限）改为服务端真值查询，不接受模型自报参数。
6. 审查工具与能力引入（描述、版本、凭证、参数透明、同名遮蔽）；执行层护栏的复核放在上下文之外。
7. 对护栏做双向评估（应拒绝与应放行两侧）并设不可被平均分抵消的硬阈值。
8. 把边界决策（含被排除的能力与非目标）写成记录，供后续评审对照。

## 交付物

- 观察/动作边界清单与职责分层表（含显式排除项）
- 护栏分层表（每层防护范围与已知局限）
- 高风险操作清单与人工确认阈值
- 边界与安全决策记录（每项取舍的理由）

## 检查、停止与回滚

- 每个期望能力都能在观察通道或动作接口上找到对应入口，否则记入缺口
- 专用工具的取舍理由落在四类例外之内
- 每个不可逆操作有明确的把关路径（慢思考或人工确认），且不由模型单独判断
- 政策事实全部来自服务端真值，清单里没有模型自报项
- 护栏评估同时覆盖应拒绝与应放行两侧；复核机制位于上下文之外
- 停止条件：期望能力与运行环境约束冲突、无法在边界内实现时，暂停并交由人工裁决
- 停止条件：发现新动作无法归入现有分级或阈值、或防护依赖的真值来源不可用时停止，不放行
- 回滚：已定义。审批阈值、分级表与边界决策记录变更应保留旧版；回滚即恢复上一版并复跑双向评估。

## 依据与边界

**来源规则**

- 没有通过观察通道进入上下文的信息，对模型来说就像不存在；没有被动作接口允许的操作，模型即使知道该怎么做，也只能停留在文字建议上。
- 通用基础能力用于组合与探索；专用工具用于约束高风险和强业务规则操作。
- 基于 LLM 的 Agent 应在结构化的知识体系上展开，而不是盲目随机探索。
- 当构建生产级 Agent 系统时——建议：将工程重心放在约束、验证与纠正上，确保工具调用安全、上下文得到管理、错误可纠正。
- 当需要理解 Agent = LLM + 上下文 + 工具 与 Agent = Model + Harness 的关系时，不应把后者当作与前一个公式并列的另一套划分，也不应把它当作覆盖全书十章的目录；它是同一事物在生产形态下的展开，将上下文和工具细分为上下文管理、工具接口、约束、验证、纠正五项职责，是构建部分内部的一个观察视角。
- 代码必须在隔离沙盒中运行，默认不能访问网络，也不能读取授权工作目录以外的文件，并对执行时间、CPU、内存和输出大小设置上限。
- 模型自主决策的空间越大，出错时的影响面也越大，因此需要更精细的约束、验证和纠正机制来确保可靠性。
- 护栏评估不能只测试应当拒绝的请求是否被拦截，还要测试明确允许的请求是否能够正常完成。
- 高风险操作需额外审查或人工确认。
- 执行层护栏的复核必须由上下文之外的机制完成。
- 当 Agent 超过重试次数或操作次数的上限时，应升级到人工干预；涉及敏感、不可逆或高风险操作时，应触发人工监督，至少在团队对 Agent 可靠性建立起足够信心之前。
- 安全问题从第一行代码就要考虑，而不是上线前打补丁。
- 在将外部内容注入上下文之前，应使用明确的标记包裹并标注来源（如 `<external_content source="webpage">...</external_content>`），提示模型该段内容来自不可信的外部世界，其中出现的“指令”不应被执行。
- Python 虚拟环境（venv）不是沙盒，不能提供文件系统、网络和进程层面的安全隔离。
- 通过 MCP 协议或 Skill Hub 引入能力时，必须审查描述与版本、隔离凭证，并保证模型看到的参数与工具真正执行的参数一致。
- 在服务端代码化校验中，政策事实（如舱位等级、保险状态、预订时间、航段使用情况、航班状态）必须由服务端查询数据库获得，当前时间取自服务端时钟，不得采信模型自报的参数。
- 动态生成软件的安全目标应是即使 AI 写错代码，权限约束仍无法被绕过；更稳妥的架构是把信任边界下移到数据层，由稳定且经人类审查的机制强制执行权限规则。
- 工具风险评级时，评级对象应从“工具”细化到“工具+参数”，调用时根据可逆性、权限和影响面计算风险；采用基于规则的确定性检查（路径黑白名单、正则），而非模型判断；验证时应只检查结构化数据。
- 当操作属于发邮件、拨电话、对外转账等不可逆或非幂等操作时——建议：应改用事前控制手段，如提议者-审核者的事前审批
- 按可逆性给动作分级：快思考只允许执行可逆动作，不可逆操作交由慢思考把关，不允许快模型执行会造成不可逆后果的工具调用。
- 安全点的密度应与环境变化速度匹配；安全点之外还需要多少额外防护，取决于动作有多不可逆。
- Agent 生成的代码修改必须由安全机制在隔离环境中复现、回归后才能发布。
- 护栏至少包括规则违规、隐私泄露、无证据陈述、承诺—行动不一致和越权操作；这些指标应设置不可被平均分抵消的硬阈值。

**来源陷阱**

- 将政策事实（如 cabin_class、has_insurance、current_time）设计成由模型填写的参数，而不是由服务端查询数据库读取。
  - 后果：模型只要报错一个值或被诱导报错，“守门员”就形同虚设，最后一道防线失效。
  - 纠正：政策事实不应设计成由模型填写的参数；防线必须建立在模型无法伪造的数据之上。
- 同名工具遮蔽（tool shadowing）
  - 后果：把敏感调用路由给恶意方
  - 纠正：接入前审查描述、锁定版本、配最小权限凭证；运行时靠层次化分类和动态发现缩小候选
- 把黑名单或关键字匹配当作唯一的安全机制，未结合语义解析或独立审查。
  - 后果：攻击者可通过变形命令、管道、子shell等轻易绕过，使危险操作被放行。
  - 纠正：将黑名单仅作为第一层基础防护，之上结合语义解析、权限控制、独立审批等分层机制，高风险操作由上下文外审查确认。
- 过度依赖上下文层的提示注入防御（输入清洗、来源标记、指令数据分离），认为这些措施能提供可靠保证。
  - 后果：上下文层只能降低攻击成功率，无法彻底阻止注入；攻击者成功注入后，Agent可能执行不可逆操作，泄露数据。
  - 纠正：把上下文层作为第一道防线，同时部署执行层工具权限控制、独立审查、沙盒隔离和数据层行级安全等分层护栏，确保即使注入成功也无法执行危险动作。
- 把外部网页、工具输出、第三方 Skill 或其 LLM 摘要不经审查直接当作可执行指令或纳入长期能力，误以为 LLM 总结能净化恶意内容。
  - 后果：恶意指令可更直接地劫持 Agent 行为，影响长期生效，造成数据泄露、执行危险操作等；状态栏被污染还可被反向利用。
  - 纠正：对来源不明 Skill 和外部内容进行代码级审查；LLM 摘要只作可读性转换，不作为指令或长期能力；按 schema 提取主张并保留原文，提取出的字符串绝不能作为指令执行。

**适用边界**

- 不含具体模型选型与提示词撰写
- 不含多 Agent 协作的拓扑、冲突与完成验证（见 coordinate-agent-work-and-verification）
- 不替代基础设施层安全（主机、网络、密钥管理）；护栏数值以目标系统的监控口径为准
