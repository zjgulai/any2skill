# 渲染、验证并安全交付生成产物

## 何时使用

- Agent 生成代码或界面后需要判断真实渲染/执行效果时
- 产物由数据库、浏览器等外部环境直接执行（SQL、前端代码）时
- 前端遭遇无法解析的数据格式、需要设计自修复与上报机制时
- 评估「生成 + 审核」闭环的完备性时

## 输入与前置条件

- 生成产物的形态（代码、界面描述、SQL、文档）与执行/渲染环境
- 产物的信任边界（谁执行、以什么权限执行）
- 既有验证手段（测试、渲染截图、linter）

## 执行步骤

1. 明确产物形态与信任边界：界面类优先声明式描述（如界面 JSON 由受信组件目录渲染），确需任意 HTML/代码时限定在沙盒中展示或执行。
2. 把大体积中间计算交给执行环境（数据库、浏览器）直接完成，避免经模型搬运数据。
3. 在隔离环境中渲染或执行产物，收集真实效果（布局溢出、解析失败、运行错误）。
4. 失败时不显示空白或静默兼容：把原始样本与详细报错上报给 Agent 作为修复输入；适应机制与报告并行，不能吞掉异常信号。
5. 自修复分两段：先用确定性检查覆盖高频问题，再把长尾交由模型分析生成修复。
6. 验证通过后进入交付；交付门槛（隔离复现、回归、发布控制）由安全机制把关，不在本流程内代行。

## 交付物

- 渲染/执行验证记录（发现的问题与证据）
- 失败上报格式（原始样本、报错、上下文）
- 修复方案与其确定性/模型分段归属

## 检查、停止与回滚

- 产物在隔离环境真实渲染/执行过，验证的是实际效果而不是代码表面
- 失败路径产生可复现的上报，且适应行为未吞掉异常信号
- 声明式路径下不执行任意代码；沙盒路径有明确边界
- 高频问题的修复由确定性检查先处理，模型兜底只接长尾
- 停止条件：产物需要超出沙盒边界的权限才能验证时，暂停并交由人工决定放宽范围
- 停止条件：渲染环境不可用、无法产生真实效果证据时停止，不以静态检查冒充渲染验证
- 回滚：已定义。自修复对既有解析器/组件的改动应保留旧版；回滚即恢复上一版并保留上报记录以复评。

## 依据与边界

**来源规则**

- 模型与脚手架之间是此消彼长的关系：模型足够强时脚手架可以更薄；模型不够强时，应把关键的逻辑推理交给代码和约束求解器来保证正确性。脚手架该做多厚取决于模型的能力边界。
- 在代码驱动的多媒体生成中，仅生成代码不够，必须引入渲染与审核机制以发现渲染效果问题。
- 当前端遇到无法解析的日志格式时，不显示错误，而是自动将失败信息（原始日志样本、详细报错）报告给 Agent。
- 构建 Agent 自我修复能力时，应先用确定性检查覆盖高频问题，再将确定性规则未覆盖的疑难问题交给 LLM 分析并生成修复方案，两层配合以稳定修复常见问题并应对长尾疑难。
- 当 Agent 编写新 Agent 时，应提供高质量 Agent 实现作为参考范例，在其基础上针对性修改，而不是在提示词中穷尽所有规则或从零开始编写。
- 在处理日志解析的格式变化时，Agent 的适应机制必须与报告并行，不能让适应机制吞掉异常信号。
- Agent 生成 HTML/UI 时，优先采用 A2UI 类声明式协议，只输出界面描述 JSON，由客户端用受信组件目录渲染，不执行任意代码；确需任意 HTML 时应在沙盒环境中展示。

**适用边界**

- 不是前端组件库或设计系统技能，不产出 UI 组件实现
- 不含发布权限、密钥与回归门槛的实施（属安全机制，见 secure-agent-actions）
- 不覆盖服务端数据校验的事实来源设计（见 secure-agent-actions）
