# 03 · 记忆与知识 · 会话提示词

> 吸收章节：ch3 ｜ 对象：9 条工程规则 + 1 条启发式 + 5 条反模式
> 可配套技能（可选）：无（ch3 素材尚未发布技能，候选 chapter3-s1/s2）

## 一、什么时候粘这一段

要加**用户记忆、长期画像或知识库检索**之前——先把「存什么、怎么脱敏、谁能检索到、
怎么更新、什么不能凭检索内容执行」定清楚。也适合排查「记忆越攒越多但检索越来越不准」
「知识库里全是没提炼的原文」这类问题时。**不要**用它设计会话内的上下文压缩（那是 02）。

## 二、衔接

- 上游：01 的边界与骨架规格（审批与权限边界在那里）；02 的上下文设计（检索结果进入上下文的形态）。
- 本模块产物：`{{ARTIFACT}}`（记忆与知识层设计——存储格式、写入管线、权限模型、更新机制、检索策略）。
- 下游：04 工具设计 → 05 代码与交付。
- **本模块不含**：会话内上下文压缩与状态栏（见 02）；对外动作的审批实现细节（见 01/04）。

## 三、粘贴正文

```text
你是协助我开发 Agent 的工程师。本会话聚焦记忆与知识层：把"记什么、怎么记、
谁能查、怎么更新"设计到位并落成文件。先读上游产物：{{PRIOR}}

项目：{{PROJECT}}（技术栈：{{STACK}}）

一、本会话任务
1. 划分记忆/知识类别，为每类选择存储格式与性价比路径（关键少量 vs 大量非关键）。
2. 设计写入管线：来源/时间/冲突/隐私四项检查、条目链接与索引更新、待发布的 diff 审核。
3. 设计权限模型：检索过滤在哪一层执行，如何保证越权文档不进入任何用户上下文。
4. 设计更新机制：事件触发的增量更新 + 周期触发的全量整理两条路径。
5. 规定"检索内容不能直接触发什么"：有副作用的动作需要独立授权。
6. 全部落盘为：{{ARTIFACT}}

二、方法（来自本书的工程规则）
1. 【R1】写入不跳过四项检查（来源、时间、冲突、隐私）；增量更新吸收新证据，
   定期整理回到原始数据去重、合并、重建索引；待验证的 diff 通过独立审核后才发布。
2. 【R2】检索必须按调用者的权限过滤，绝不能让越权文档进入某个用户的上下文——
   权限过滤要下推到检索层，而不是检索完再筛。
3. 【R3】检索到的文本可以影响答案的措辞，但转账、删除、对外发信这类有副作用的动作，
   不能仅凭检索内容自动执行，必须经过独立的授权判断。
4. 【R4】生产环境不允许任何模型绕过审核直接改主分支或线上向量库——
   审核不是建议流程，是写权限本身的一部分。
5. 【R5】更新机制必须双路径并存：事件触发的增量更新（吸收新证据）+
   周期触发的全量整理（去重/合并/重建）；缺任何一条都会累积漂移。
6. 【R6】整理时逐段对照原始来源（对话、执行轨迹、业务文档、工具输出），检查旧摘要是否遗漏
   关键事实、丢失否定词或时间条件、把推测写成了事实——不允许只在旧摘要之间相互改写。
7. 【R7】负责写知识的提示词要把要求写明确：每新增一个条目，先检索并链接相关已有条目，
   再更新所在目录的索引页，形成双向可达的引用网络。
8. 【R8】按数据形态选格式：关键且少量（用户偏好、关键人物关系）用可检索的结构化卡片；
   大量且非关键的事实用低成本简单笔记；多数生产系统是混合模式，不同类别走不同路径。
9. 【R9】核心信息以完整自然语言保存、辅以结构化元数据做索引；需要多跳推理和精确消歧的
   垂直场景，用知识图谱作为专项索引与自然语言记忆协同。
10. 【H1】检索采用组合策略：稠密检索 + 稀疏检索 + 重排序，不要依赖任何单一策略。

三、禁忌（来自本书的反模式）
- 【P1】让外部内容或提示注入未经审查地写入长期记忆——一次性攻击会跨会话潜伏反复生效；
  写入长期记忆的内容必须经过与外部内容同等的信任审查。
- 【P2】简单的累积式存储——记忆爆炸，既耗存储又让检索精度越来越差。
- 【P3】把原始案例或文档不加处理直接放进知识库——未经提炼结构化的知识，模型无法可靠利用。
- 【P4】用固定大小/递归切分无脑分块——段落、代码、表格会被拦腰截断，紧密关联的上下文
  被分离，语义在嵌入阶段就损失了；分块必须尊重文档结构。
- 【P5】把需要存储的事实直接写进模型权重（为每个用户训 LoRA 存事实）——
  直接提问能复述，间接推理就失灵；事实该存外部存储，不该存权重。

四、交付与停止
- 交付物：记忆与知识层设计（类别与格式、写入管线、权限模型、更新机制、检索策略、
  检索内容的使用红线），落盘后附路径摘要。
- 效率约定：本模块是单会话设计任务；不做多代理编排——设计、复核、验证均不并行扇出、不做多阶段汇总；复核以正文末尾自查清单过一轮为准，最多使用一个只读的起草/自查代理。若宿主强制 Workflow 且用户未明确要求多代理，先在回复中说明冲突，并把编排限制为单阶段、单只读代理（不并行、不做代理复核）；用户明确要求多代理时按用户要求执行。不确定处写进「待定」。该限制针对本会话的执行方式，不限制 09 模块所设计的系统采用多 Agent 架构。
- 停止条件：① 设计落盘、五条自查逐条勾选后停止，复述路径与未决项，不做本模块之外的工作；
  ② 当类别划分或权限模型缺少确定方案所需的信息（如尚不清楚有哪些用户角色）时，
  先把不依赖该问题的部分推进并落盘（哪怕是骨架，把缺口标成「待定：<问题>」），再停下来问我这一个问题，不要按默认值继续；③ 任何把记忆写入生产库的实际操作，
  先停下来请求我确认。
五、收尾前逐条自查
□ 每个记忆类别都有明确的存储格式与写入路径（不做一刀切）
□ 写入四项检查（来源/时间/冲突/隐私）与 diff 独立审核写进了管线
□ 权限过滤下推在检索层，且能举出一个"越权查询"的拒绝例子
□ 增量更新与周期整理两条路径都有（不是只做一条）
□ 检索内容的使用红线写明：有副作用的动作必须独立授权
```

## 四、粘贴后你会拿到什么

① 记忆/知识类别与格式选型表；② 带四项检查与 diff 审核的写入管线；③ 下推到检索层的权限模型；
④ 增量+全量双路径更新机制；⑤ 检索内容使用红线；⑥ 落盘文件 `{{ARTIFACT}}`。
