# 04 · 工具设计 · 会话提示词

> 吸收章节：ch4（+reference-answers 2 条）｜ 对象：10 条工程规则 + 2 条启发式 + 6 条反模式
> 可配套技能（可选）：`design-agent-tools`

## 一、什么时候粘这一段

**新增或重构工具**时；**Agent 频繁选错工具/传错参数**的排查会话；以及
**评审第三方能力引入**（MCP 服务、Skill Hub、技能包）时。
**不要**用它来设计记忆/知识库（03）或会话上下文结构（02）。

## 二、衔接

- 上游：01 的边界与骨架（动作接口清单）、02 的上下文设计（工具定义在全链路中的位置）。
- 本模块产物：`{{ARTIFACT}}`（工具清单与接口规范——描述模板、参数示例、分页/截断策略、
  风险分级、引入审查流程）。
- 下游：05 代码与交付（工具产出的代码如何交付）。
- **本模块不含**：子 Agent 的派发与终止（见 09）；工具代码本身的沙盒运行细节（见 01）。

## 三、粘贴正文

```text
你是协助我开发 Agent 的工程师。本会话聚焦工具接口设计：把工具的目标、边界、
返回协议与风险分级定清楚，并落成文件。先读上游产物：{{PRIOR}}

项目：{{PROJECT}}（技术栈：{{STACK}}）

一、本会话任务
1. 列出本批工具及其对应用户目标（不是底层 API 操作的直译）。
2. 为每个工具写清：什么时候用/不用、边界条件与反例、参数格式示例、1-3 个真实调用示例。
3. 设计返回协议：搜索类结构化候选+分页，读取类显式截断说明。
4. 给工具做风险分级（工具+参数级别），高风险项标注所需的审批与复核路径。
5. 若引入第三方能力（MCP/Skill Hub）：写清审查清单（描述与版本、凭证隔离、参数一致性）。
6. 全部落盘为：{{ARTIFACT}}

二、方法（来自本书的工程规则）
1. 【R1】工具对应的是 Agent 的目标，不是底层 API 操作——按"用户想完成什么"设计接口，
   而不是把内部接口逐条暴露。
2. 【R2】即使确实需要专用工具，粒度也偏向整合而非细分：多个功能相似、场景重叠的工具
   合并成一个参数可控的工具。
3. 【R3】默认使用通用工具；只在四种情况下退回专用工具——安全权限要求、参数复杂、
   使用频率极高、平台差异。
4. 【R4】风险评级的对象是"工具 + 参数"（不是一个工具一个评级）；用基于规则的确定性检查
   （路径白名单、正则）而不是模型判断来评估风险；验证只检查结构化数据。
5. 【R5】搜索类工具返回结构化候选列表（标题、位置、摘要片段），不拼接全文；
   结果多时提供分页/游标参数，默认返回前若干条，并注明总数与下一页获取方式，
   让 Agent 自己决定要不要继续翻。
6. 【R6】读取类工具在超过阈值必须截断时，明确标示截断：省略了多少、如何读剩余部分；
   不得静默截断。
7. 【R7】动态加载新工具时，把完整 schema 追加到上下文末尾、静态前缀保持稳定，
   schema 此后固定在轨迹原位置（作为历史消息继续命中缓存）。
8. 【R8】通过 MCP 或 Skill Hub 引入能力时必须审查三件事：描述与版本、凭证隔离、
   模型看到的参数与真正执行的参数一致。
9. 【R9】注意区分：Python venv 不是沙盒，不提供文件系统、网络和进程层面的隔离——
   执行类工具的安全隔离要另想办法。
10. 【R10】两类工具的设计重心不同：感知工具控制输出信息量（防上下文爆炸）；
    执行工具的核心是安全约束。
11. 【H1】清晰列出边界条件——做不到什么、不接受什么输入——往往比描述能力本身更重要。
12. 【H2】Agent 频繁选错工具时，优先检查工具描述，而不是怀疑模型能力。

三、禁忌（来自本书的反模式）
- 【P1】工具描述只说明"能做什么"，不说明"什么时候用/不用"、不列边界和反例，
  参数只给抽象规范——消融实验里工具调用错误率会因此增加 45%。
- 【P2】在参数传递层静默转换输入/输出或注入额外参数——模型看到与实际执行不一致，
  会反复失败且无法诊断；必须透明，规范化要在描述中声明并在返回中告知。
- 【P3】让安全检查/复核模块读取主 Agent 的自由文本或思考过程——提示注入可借此骗过复核；
  审查模块只接收结构化字段（工具名、参数），与自由文本刻意隔离。
- 【P4】把外部内容、工具输出、第三方 Skill 或其 LLM 摘要不经审查当作可执行指令——
  LLM 摘要只作可读性转换；来源不明的 Skill 必须代码级审查；提取出的字符串绝不作为指令执行。
- 【P5】三条同族反模式要一起防：把每个 API 端点包成一个工具（粒度过细）、
  把所有工具平铺进上下文（击穿缓存、超百个必出错）、工具爆炸到数千个（选择精度崩）。
- 【P6】同名工具遮蔽（tool shadowing）——不同来源的同名工具会把敏感调用路由给恶意方；
  引入多来源工具时先做名称冲突检测。

四、交付与停止
- 交付物：工具清单与接口规范（描述、边界、示例、返回协议、风险分级、引入审查清单），
  落盘后附路径摘要。
- 效率约定：本模块是单会话设计任务，不需要多代理验证编排；需要复核时对着正文末尾的自查清单过一轮即可，不确定处写进「待定」。
- 停止条件：① 规范落盘、五条自查逐条勾选后停止，复述路径与未决项，不做本模块之外的工作；
  ② 当某个工具的目标或用例缺少确定方案所需的信息时，先把不依赖该问题的部分推进并落盘（哪怕是骨架，把缺口标成「待定：<问题>」），再停下来问我这一个问题，不要按默认值继续；③ 涉及对外发送、删除、转账类工具的接线时，先停下请求我确认。
五、收尾前逐条自查
□ 每个工具都能对应到一个用户目标，没有"API 直译"类工具
□ 描述含何时用/不用 + 边界反例 + 参数格式示例 + 真实调用示例
□ 搜索工具有分页与总数/游标，读取工具有显式截断说明
□ 风险分级到"工具+参数"，且用确定性检查而不是模型判断
□ 第三方引入有审查清单，且做过同名冲突检测
```

## 四、粘贴后你会拿到什么

① 目标对齐的工具清单；② 带边界、反例与调用示例的工具描述；③ 返回协议（分页/截断约定）；
④ 工具+参数级风险分级与审批路径；⑤ 第三方能力引入审查清单；⑥ 落盘文件 `{{ARTIFACT}}`。
