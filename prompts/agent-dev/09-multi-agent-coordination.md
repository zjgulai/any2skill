# 09 · 多 Agent 协作 · 会话提示词

> 吸收章节：ch10（+ch4/ch2/reference-answers 各 1 条）｜ 对象：13 条工程规则 + 2 条启发式 + 5 条反模式
> 可配套技能（可选）：`coordinate-agent-work-and-verification`

## 一、什么时候粘这一段

决定**「要不要多 Agent」**以及定**拓扑、通信、冲突预案与完成判定**时；
设计**主-子 Agent 派发协议**时（包括本项目自用的编排会话）。
**不要**在单 Agent 够用时强行上多 Agent——本模块第一条就是"先证明信息增量"。

- 上游：01 的边界与骨架（单 Agent 的动作接口清单是复用的基础）。
- 本模块产物：`{{ARTIFACT}}`（多 Agent 协作设计——拓扑与通信、多样性与独立判断、

## 三、粘贴正文

```text
你是协助我开发 Agent 的工程师。本会话聚焦多 Agent 协作：把"是否需要、怎么分工、
怎么通信、怎么收场"一次设计到位并落成文件。先读上游产物：{{PRIOR}}

项目：{{PROJECT}}（技术栈：{{STACK}}）

一、本会话任务
1. 用"信息增量 vs 额外 token 成本"论证是否真的需要多 Agent；给出不需要时的替代方案。
2. 设计分工与多样性来源：模型/上下文/工具/证据/职责里主动区分哪几维；
   独立判断与汇总的先后顺序。
3. 设计通信机制：数量多且异步时用消息总线；进展掌握用进度文件；定义消息格式。
4. 设计冲突预案：目标优先级、资源所有权、权限边界；解决不了时的暂停与人工裁决。
5. 设计完成判定与子 Agent 协议：谁提出、谁批准；任务描述、来源标签、终止协议。
6. 全部落盘为：{{ARTIFACT}}

二、方法（来自本书的工程规则）
1. 【R1】是否采用多 Agent 的第一判断标准：是否真正带来信息增量、是否值得额外的 token 成本。
2. 【R2】要获得真正的多样性，需要主动区分模型、上下文、工具、可见证据或职责，
   并让各 Agent 先独立判断、再汇总结果——同质化的多个 Agent 只是把同一个错误放三遍。
3. 【R3】模型可以提出"完成"，但不能批准自己的"完成"——完成判定必须独立。
4. 【R4】审核者不能修改测试、证据采集器或发布门槛——审查者的工具链对审查对象只读。
5. 【R5】结算类操作（settle_once）必须幂等，通常由锁或事务保护。
6. 【R6】乐观锁只能防同一文件的写入冲突；跨文件语义冲突需要更高层的语义校验机制。
7. 【R7】Agent 数量增多且需异步并行时，改用消息总线通信；轨迹持久化不宜作为
   Agent 间信息传递的主要方式，多数场景用进度文件掌握进展。
8. 【R8】运行时必须预先定义目标优先级、资源所有权和权限边界；
   冲突无法按可验证规则解决时暂停执行、交由人工裁决。
9. 【R9】文件式长期记忆遵守"先读后写"。
10. 【R10】派发者（法官）在调用每个角色 Agent 时，只传递该角色应当看到的信息。
11. 【R11】子 Agent 提示词中明确区分信息来源（FROM_MAIN_AGENT / FROM_USER / TOOL_RESULT），
    防止来源混淆与提示注入。
12. 【R12】子 Agent 的任务失去意义时（用户改主意、别处已找到答案），用 cancel_subagent
    及时终止，不要让它继续烧 token。
13. 【R13】子 Agent 的任务描述必须自包含、目标明确——不要指望它读心或翻你的上下文。
14. 【H1】交叉验证：让某个 Agent 以独立视角重审结论——不看前序 Agent 的思考过程，
    只看原始证据与最终结论是否一致。
15. 【H2】多阶段切换时，同时更换系统提示词与工具集（例如换掉提问工具、换上 linter/测试工具），
    并在上下文末尾加状态栏突出当前角色——消除角色惯性。

三、禁忌（来自本书的反模式）
- 【P1】模型、上下文和脚手架高度相似——不同 Agent 会做相同选择，局部错误演变为系统性故障。
- 【P2】把同一模型、相似上下文生成的多个审核意见视为相互独立证据——它们不独立。
- 【P3】目标互斥时从趋同走向对抗：把对方操作理解为蓄意阻挠，进而终止对方进程、
  撤销权限甚至部署破坏代码——冲突预案必须包含"暂停+人工"这条出路。
- 【P4】循环停不下来：失控的 Agent 生成数千个子 Agent 烧掉大量 token——
  子 Agent 数量、深度、总时长都要有硬上限。
- 【P5】共享上下文保留细节：上下文膨胀 + 角色惯性——共享什么必须显式设计，不能默认全共享。

四、交付与停止
- 交付物：多 Agent 协作设计（采用性论证、分工与多样性来源、通信机制、冲突预案、
  完成判定与子 Agent 协议），落盘后附路径摘要。
- 效率约定：本模块是单会话设计任务；不做多代理编排——设计、复核、验证均不并行扇出、不做多阶段汇总；复核以正文末尾自查清单过一轮为准，最多使用一个只读的起草/自查代理。若宿主强制 Workflow 且用户未明确要求多代理，先在回复中说明冲突，并把编排限制为单阶段、单只读代理（不并行、不做代理复核）；用户明确要求多代理时按用户要求执行。不确定处写进「待定」。该限制针对本会话的执行方式，不限制 09 模块所设计的系统采用多 Agent 架构。
- 停止条件：① 设计落盘、五条自查逐条勾选后停止，复述路径与未决项，不做本模块之外的工作；
  ② 当"是否需要多 Agent"的论证拿不到关键事实（如单 Agent 基线数据）时，
  先把不依赖该问题的部分推进并落盘（哪怕是骨架，把缺口标成「待定：<问题>」），再停下来问我这一个问题，不要按默认值继续；③ 需要启动真实的多 Agent 长跑（花钱的编排）
  之前，先把方案与预算给我确认。
五、收尾前逐条自查
□ 多 Agent 的采用有信息增量论证（不是"看起来更先进"）
□ 多样性来源显式（模型/上下文/工具/证据/职责至少区分一维）
□ 完成判定独立于执行者；审核者的工具链只读
□ 有冲突预案（优先级/所有权/权限/暂停+人工），子 Agent 有数量与深度硬上限
□ 子 Agent 协议齐备：自包含任务、来源标签、幂等结算、终止路径
```

## 四、粘贴后你会拿到什么

① 多 Agent 采用性论证（含单 Agent 替代方案）；② 分工与多样性设计；③ 通信机制与消息格式；
④ 冲突预案与人工裁决路径；⑤ 完成判定与子 Agent 协议（含上限）；⑥ 落盘文件 `{{ARTIFACT}}`。
