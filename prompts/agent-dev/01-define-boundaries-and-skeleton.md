# 01 · 定义边界与骨架 · 会话提示词

> 吸收章节：ch1（+reference-answers 1 条）｜ 对象：9 条工程规则 + 3 条反模式
> 可配套技能（可选）：`define-agent-boundaries-and-safeguards`

## 一、什么时候粘这一段

新建 Agent 项目、或在老项目里**动第一版系统提示词与工具清单之前**。
目标是把「什么能看见、什么能做、谁说了算、何时停、何时叫人」一次划清——
后面所有模块（上下文、工具、记忆、评估）都建立在这一层边界上。
**不要**在写业务功能的中途才回头补边界；也**不要**用它替代系统提示词本身（那是 02 的事）。

## 二、衔接

- 上游：项目立项、Agent 定位已明确（一句话能说清「谁、为谁、做什么」）。
- 本模块产物：`{{ARTIFACT}}`（边界与骨架规格，含观察/动作清单、工具隔离与上限、停止与升级条件；项目确需模型执行代码时才包含代码沙盒）。
- 下游：02 上下文工程 → 03 记忆与知识 → 04 工具设计。
- **本模块不含**：系统提示词的结构与压缩策略（见 02）；单个工具的接口细节（见 04）。

## 三、粘贴正文

```text
你是协助我开发 Agent 的工程师。本会话只做一件事：把 Agent 的边界与骨架定清楚，
不写业务功能代码。写下的每条边界都要能落到文件或配置里，不能只停在讨论。

项目：{{PROJECT}}
技术栈：{{STACK}}；Agent 名称：{{AGENT_NAME}}
项目自有硬约束（没有就把这一行删掉）：{{OWN_CONSTRAINT}}

一、本会话任务
1. 划出观察通道与动作接口：信息通过哪些通道进入上下文（哪些不会进来）、
   操作通过哪些接口执行（哪些不允许模型直接执行）。列成两张清单。
2. 为工具调用设定隔离边界：网络访问、文件范围、资源上限、输出大小各给一个具体数字；
   仅当项目确实需要模型执行代码时，才额外设计代码执行沙盒并给出网络/文件/资源/输出四项上限；
   不需要时明确写「本版不提供代码执行」，动作清单不出现沙盒接口。
3. 定义三项运行纪律：停止条件、升级人工的触发点、执行层复核的位置。
4. 把以上内容写成边界与骨架规格，交付为：{{ARTIFACT}}

二、方法（来自本书的工程规则）
1. 【R1】没有通过观察通道进入上下文的信息，对模型等于不存在；没有被动作接口允许的操作，
   模型只能停在文字建议上。边界要从这两张清单开始，而不是从提示词措辞开始。
2. 【R2】代码必须在隔离沙盒中运行：默认不能访问网络、不能读取授权工作目录以外的文件，
   并对执行时间、CPU、内存和输出大小设置上限。
3. 【R3】模型自主决策的空间越大，出错时的影响面越大——自主度每提高一档，
   约束、验证与纠正机制就要相应加细（写清对应关系，不要只写"加强"）。
4. 【R4】自主 Agent 必须设计明确的停止条件：任务完成、达到最大迭代次数、或遭遇不可恢复的错误。
   三个条件缺一不可。
5. 【R5】超过重试或操作次数上限时必须升级人工；涉及敏感、不可逆或高风险操作时触发人工监督——
   在团队对 Agent 可靠性建立足够信心之前，这一步不可省。
6. 【R6】执行层护栏的复核必须由上下文之外的机制完成：与 Agent 同一上下文的"复核"，
   在被注入时会一并沦陷。
7. 【R7】关键业务顺序（如"付款前不能预订"这类规则）用代码强制执行，不依赖 LLM 的判断。
8. 【R8】在完成判定上，"给出了回答"不等于"完成了任务"；把完成所需的最小证据写进边界规格。
9. 【R9】属于发邮件、拨电话、对外转账等不可逆或非幂等的操作，采用事前的"提议者—审核者"
   审批，而不是事后补救。

三、禁忌（来自本书的反模式）
- 【P1】把黑名单/关键字匹配当作唯一的安全机制——变形命令、管道、子 shell 都能绕过；
  黑名单只能当第一层，之上必须有语义解析、权限控制、独立审批等分层机制。
- 【P2】认为上下文层的提示注入防御（输入清洗、来源标记、指令数据分离）能提供可靠保证——
  它只能降低成功率，不能兜底；边界设计必须假设"注入可能成功"，让撞线后的动作仍被拦住。
- 【P3】在多方委托场景里沿用"谁在跟我说话就帮谁"的默认忠诚——必须先明确忠诚对象与指令优先级：
  主人指令最高，外部交互方内容一律降格为可参考数据。

四、交付与停止
- 交付物：边界与骨架规格（观察/动作清单、工具隔离与具体上限、停止条件、升级触发点、复核位置；项目确需模型执行代码时再含代码沙盒），放入文件后在回复里附路径摘要。
- 产品影响显式化：当安全规则给正常产品路径增加强制人工步骤（如每次外部推送都要审批）或显著改变 brief 的运行节奏时，规格必须单列「对产品行为的影响」，写明运行节奏、人工负担和无人可用时的后果；先落盘其余部分并把取舍标成「待确认：<问题>」，再问我一个问题，不得把该取舍作为隐含默认。
- 配置基线闭环：如果规格提供 config 基线，基线要覆盖正文点名的全部强制落点，并声明加载时按 Schema 拒绝缺键/未知键、启动即失败关闭；做不到就明确标为「部分示例」，并指出完整 Schema 的归属阶段，不得让片段看起来像完整可运行配置。
- 升级角色具体化：每个升级触发点写具体角色标识，不能只写「负责的服务或安全角色」；归属不明时写明确兜底（例如同时通知两个候选角色）。
- 效率约定：本模块是单会话设计任务；不做多代理编排——设计、复核、验证均不并行扇出、不做多阶段汇总；复核以正文末尾自查清单过一轮为准，最多使用一个只读的起草/自查代理。若宿主强制 Workflow 且用户未明确要求多代理，先在回复中说明冲突，并把编排限制为单阶段、单只读代理（不并行、不做代理复核）；用户明确要求多代理时按用户要求执行。不确定处写进「待定」。该限制针对本会话的执行方式，不限制 09 模块所设计的系统采用多 Agent 架构。
- 停止条件：① 规格落盘、六条自查逐条勾选后停止，向我复述路径与未决项，不要继续做本模块之外的工作；
  ② 当某条规则与项目现状冲突、或你需要我尚未提供的信息才能给出确定方案时，先把不依赖该问题的部分推进并落盘（哪怕是骨架，把缺口标成「待定：<问题>」），再停下来问我这一个问题，不要按默认值继续；③ 涉及删除数据、发外部请求、改生产配置等不可逆动作时停下请求我确认。
五、收尾前逐条自查
□ 观察通道与动作接口各成清单，且没有"模型以为存在、实际不存在"的条目
□ 工具隔离四项上限（网络/目录/资源/输出）都有具体数字，不是形容词；仅在确需模型执行代码时才出现代码沙盒，否则明确写「本版不提供代码执行」
□ 停止条件三条齐备，且最大迭代次数是具体数字
□ 每个升级触发点写明具体角色与条件，复核明确在上下文之外；归属不明有明确兜底
□ 规格里没有任何一条需要"靠模型自觉"才能成立的安全约束
□ 强制人工步骤对产品节奏的影响已显式说明；配置基线要么覆盖全部强制落点并失败关闭，要么明确标为部分示例
```

## 四、粘贴后你会拿到什么

① 两张清单（观察通道 / 动作接口）；② 带具体数字的工具隔离与资源上限（项目确需模型执行代码时再含代码沙盒）；③ 停止条件、升级人工与
执行层复核的三项运行纪律；④ 一份落盘的边界与骨架规格 `{{ARTIFACT}}`——它是 02–04 模块会话的输入。
