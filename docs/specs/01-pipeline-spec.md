## 问题陈述

《深入理解 AI Agent》中文正文已在本机（实测：13 个 `.md`、合计 1,102,782 字节）。但目前无人能回答两个必须可答的问题：

1. **「这条 skill 规则出自书里哪一句？」**——正文是 1.1 MB 的连续散文，任何基于它生成的结论都无法反查到具体位置。
2. **「凭什么算达标？」**——没有机器可判定的中间层，质量只能靠模型自述或人眼通读，失败时无法归因到「读错了原文」还是「归纳错了」还是「放行了坏对象」。

同时，本项目的最高价值产物（反模式清单）**在原文里并不成节存在**：全书「常见陷阱」字面 0 命中，显式失败小节仅 13 处且高度集中在 chapter10（7 处），而原书 22 个 skill 每一个都有 6–8 条反模式。这意味着「把文中的段落抄出来」这条路在物理上产出不了需要的对象——必须有显式的综合步骤，且必须有机制能证明综合出来的东西没跑偏。

用户当前面对的具体困境是：**手里有一本书和一套设计，但没有任何一段可执行、可复跑、可审计的链路**。

## 解决方案

交付一条**单命令的提取流水线**，把「一个内容源文件」编译为「一组类型化、带物理溯源、经机器验证的知识对象」：

```text
any2skills <源文件>
   │
   ├─ 第 1 层 确定性结构层（无 LLM）
   │     产出：章节/小节锚点索引，每个锚点带行号区间与内容哈希
   │
   ├─ 第 2 层 LLM 综合层（全链路唯一非确定性环节）
   │     产出：类型化知识对象，每个对象强制携带 sourceRefs + 逐字 evidenceQuote
   │
   └─ 第 3 层 机器验证层（无 LLM 判定 + 独立判定者，= 门禁一）
         产出：验证回执；不通过的对象被拒并留下结构化拒绝理由
   │
   ▼
退出码 0 = 全部对象通过；非 0 = 有对象被拒
```

从用户视角，这条命令解决的是：**「书」变成了「带出处的知识对象，且每一个都附一张我自己能复核的体检报告」**。它不产出 skill——它产出的是 skill 唯一可信的原料，以及证明这些原料可信的证据。

关键区别只有一条，也是本项目与「让大模型直接读文档写 skill」的分界：**中间存在一个机器可判定的 IR**。因此上面两个问题从「无法回答」变成「一条命令 + 一次查表」。

## 实现决策

### D1 · 唯一接缝：一条 CLI 命令

对外只暴露**一个**命令入口，覆盖第 1/2/3 层。三段作为**可独立重跑的阶段**存在于命令内部，而不是三组独立命令。

理由：接缝数=1（`to-spec` 的理想值）；同时第 1、3 层的确定性使其必须可脱离第 2 层复跑（见 D2、D6）。命令的参数面必须能表达「跑到哪一层停」。

产物落盘位置遵循 ADR-002 的平面隔离：锚点索引与知识对象落 `pipeline/knowledge/`，验证回执落 `pipeline/registry/`。

### D2 · 三段的确定性与非确定性边界

| 层 | 是否用 LLM | 可复现要求 |
|---|---|---|
| 第 1 层 结构层 | 否 | **逐字节可复现**：同一输入两次运行产出完全相同 |
| 第 2 层 综合层 | **是（全链路唯一）** | 不要求复现；产出固化落盘，重跑须显式指定 |
| 第 3 层 验证层 | 见 D6 | 确定性判据部分逐字节可复现 |

第 1 层不使用 LLM 的物理基础（实测）：正文有 100 个 `##`、193 个 `###`、32 个 `####` 标题行，结构规整；`chapter4.md` 的 `## 工具设计的通用原则` 下辖三个 `###` 小节，行号区间为 38–69 / 70–87 / 88–99。

### D3 · 锚点索引的形状

锚点条目至少含：稳定锚点标识、源文件相对标识、标题层级、标题原文、起始行、结束行、**该锚点区间内容的哈希**。

两条关键约定：

- **锚点标识的稳定性**：标识由「源文件 + 该文件内的小节序号」构成，**不含行号**。行号仅作为定位数据存在。这样文件重排版时标识不变，失效检测交给内容哈希而不是行号比对。
- **哈希的作用**：哈希覆盖锚点区间内容。源文件改动后重跑第 1 层，哈希变化的锚点即可判定为失效，从而回答「是否与源版本一致」。

标题行原文实测形态（含中文、全角冒号、方括号标记）：`# 后记：回到 Agent = LLM + 上下文 + 工具 {.unnumbered}`。锚点解析必须能处理这类非规范标题，不得假定纯 ASCII。

### D4 · 知识对象模型：9 种类型

> **更正留痕（2026-10-08，卡 05 期间）**：本标题原文为「8 种类型」，**实测为假**。
> 正文与实现自始就是 9 种——本节下一段即写明「本规格实际提取 9 种类型（7 + `EngineeringRule`
> + `AntiPattern`）」，`pipeline/schemas/` 下也确有 9 份类型 schema（另有 `common` 与
> `knowledge-object` 两份公共文件，共 11 份）。改的是标题，不是口径；正文一字未动。
> 核实方式：`ls pipeline/schemas/*.schema.json | wc -l` → 11；`object-contract.OBJECT_TYPES.length` → 9。

对象**类型集合封闭**。采纳 ADR-003 的 7 类型为核，追加 3 个书籍型对象；其中 `SkillCandidate` 属环 3，不在本规格范围内。

⇒ **本规格实际提取 9 种类型**（7 + `EngineeringRule` + `AntiPattern`）。

本规格提取的 7 种既有类型及其必填字段：

| 类型 | 必填字段 |
|---|---|
| `Concept` | `canonicalTerm` / `aliases` / `definition` / `examples` |
| `Metric` | `name` / `formula` / `inputs` / `unit` / `window` / `failureModes` |
| `MentalModel` | `trigger` / `inputs` / `reasoning` / `limits` / `counterexample` |
| `DecisionModel` | `inputs` / `branches` / `outputs` / `unknownPolicy` / `stopConditions` / `reviewState` |
| `Heuristic` | `trigger` / `recommendation` / `confidence` / `exceptions` |
| `Case` | `title` / `context` / `facts` / `decisions` / `outcome` / `evidenceRefs` / `limitations` / `dataClass` |
| `Playbook` | `title` / `prerequisites` / `steps` / `checks` / `rollback` / `approval` |

本规格新增的 2 种（合计 9 种）：

| 类型 | 必填字段 |
|---|---|
| `EngineeringRule` | `statement` / `rationale` / `appliesWhen` / `violation` / `chapterRef` |
| `AntiPattern` | `pattern` / `harm` / `corrective` / `evidence` / `chapterRef` |

`SkillCandidate`（`skillId` / `sourceObjects[]` / `trigger` / `chapterRefs[]` / `promotionState`）**本规格不产出**，仅要求对象层能为其提供依据（见「范围之外」）。

### D5 · 公共契约与三者边界判据

每个对象强制携带公共字段：`id` / `objectType` / `revision` / `status` / `createdAt` / `sourceRefs`（对齐 Kb2Agent `baseObject` 的 6 项必填），并按需携带 `evidenceGrade` / `freshness`。

- `status` 取值集合采纳既有枚举：`draft` / `candidate` / `approved` / `superseded` / `blocked`。
- `identifier` 正则采纳既有约定：`^[A-Z][A-Z0-9]*(?:-[A-Z0-9]+)+$`。
  **注意**：该正则**只约束对象 `identifier`**；`sourceRefs[].anchor` 是项目内部引用约定，可含中文字符，两者不得混为一谈。
- `hash` 统一使用 `sha256:` 前缀（用于锚点内容哈希与源文件哈希）。

三者边界判据（防提取时乱分类，ADR-003 已定，本规格沿用）：

```text
可证伪且无概率                      → EngineeringRule
有置信度（0–1）或例外               → Heuristic
多分支选择且需输入输出契约          → DecisionModel
```

`MentalModel` 强制要求 `limits`（失效边界）与 `counterexample`（反例）——本规格保留该约束，理由：它堵死「只说好处不说边界」这一 AI 生成内容的最常见缺口。

### D6 · 第 3 层验证：分层判据

第 3 层拆成**确定性判据**与**判定者判据**，分两组独立执行。

**确定性判据（无 LLM）：**

| 判据 | 失败后果 |
|---|---|
| 对象通过其类型的 schema 校验 | 拒绝 |
| `identifier` 符合正则 | 拒绝 |
| `sourceRefs` 可解析到第 1 层锚点 | 拒绝 |
| 锚点内容哈希与索引一致 | 拒绝（标记为**所依赖源版本已变更**，理由码独立） |
| `sourceRefs` 非空 | 拒绝，**无豁免** |
| `evidenceQuote` 在锚点区间内**逐字命中** | 拒绝 |

逐字命中是本层的主力判据：它把「出处写了但内容对不上」从主观判断变成字符串比对。

> **口径补充（2026-10-08，卡 04 期间按实测修订）**
> 比对时**忽略 markdown 强调标记与空白差异**（归一化标识 `markdown-emphasis+whitespace`），
> 依据是实测：两轮 `chapter4.md` 的全部 9 条引文拒绝，逐字符比对后差异**只有 `**`**
> （相似度 0.90–0.98），去掉标记后 9 条全部命中，**没有一条是改写或编造**。
> 维持字节相等会让被判死的对象里有 16% 死于排版标记而非知识问题——正是 D7 所说需要被
> 检测出来的 R6。放宽幅度有界：只容忍「同一段文字的两种表示」，内部删字、同义改写、
> 凭空编造一律仍被拒（`pipeline/tools/test/verifier-quote.test.mjs` 逐条钉住）。
> 回执逐对象记录 `quoteComparison`（`strict` / `acceptedBy` / `normalization` / `scope`），
> 因此「是靠归一化放过的」在审计时看得见，不必翻代码。

**判定者判据（LLM，但执行者独立于生产者）：**

判定者只接收**引文与该锚点区间的文本**，判定「该引文是否支撑该对象的主张」，输出结构化结果（支撑 / 不支撑 / 不充分 + 一句理由）。

- ADR-005 要求第 3 层的验证**必须独立于第 2 层**，不得由同一 agent 自评。
- 本规格的落实方式：判定者与生产者**不同实例、不同上下文**；判定者的输入中**不含**生产者的推理过程与提示词，只含引文、锚点文本与主张本身。
- 该独立性必须由**代码结构**保证（判定者作为独立阶段、独立上下文调用），不得只写在文档里当约定。
- 判定者判据**与确定性判据同权**：两组均须通过。这使 ADR-006 「不通过即拒绝、无豁免」在本层完整成立。

> **口径补充（2026-10-08，卡 05 期间按拍板修订）**（决策全文与理由见 ADR-010）
>
> 1. **三值的落地语义。** 本节只说「输出支撑 / 不支撑 / 不充分 + 一句理由」，并只说
>    「判定为**不支撑**时必须拒绝」，未规定「不充分」算过还是算拒。拍板为：
>    **只有「支撑」算通过**；不充分与不支撑**都拒绝**，但**分两条理由码**
>    （`JUDGE_INSUFFICIENT` / `JUDGE_NOT_SUPPORTED`）。分码的依据是修复方不同：
>    不支撑＝引文选错了（修第 2 层），不充分＝证据装不下主张（修锚点切分，或把主张写窄）。
>    混成一个码会让本规格 D7 要的可归因性失效。
> 2. **调用范围。** 缺省**短路**：只对已通过确定性判据的对象调用判定者，已被确定性判据拒绝的
>    对象记 `not-called`。`--judge-all` 打开全量并产出两组判据的交叉表。
>    短路与「两组均须通过」不矛盾——合取满足短路求值；但它有一条**代价**：
>    判定者无法推翻确定性判据的拒绝，因此「确定性判据是否过严」（R6）仍需人工看
>    `quoteComparison` 才能检出。
> 3. **判定者模型路由。** 缺省与第 2 层同路由（同模型、独立实例），但**独立可配**
>    （`ANY2SKILLS_JUDGE_*` / `--judge-model` 等）。回执必须记录判定者的 `modelId`、
>    `promptFingerprint` 与 `sameModelAsProducer`，使「同模型自审」在审计时可见。
> 4. **输入是构造的，不是删的。** 判定者输入恰好三个键（`claim` / `quote` / `anchorText`），
>    由 `object-contract.CLAIM_FIELDS` 逐类型列举主张字段。**禁止**「传整个对象再删敏感字段」：
>    删除式隔离会被将来新增的字段默默绕过。守卫是白名单（多一个键即报错），不是黑名单。
> 5. **判定者未启用时的诚实性。** 若某次运行未应用判定者判据（替身路径、`--no-judge`、
>    重判路径缺省、或注入传输不完整），回执的 `verificationGate` 必须写明本次门禁
>    **只完成了确定性那一半**，因为此时 `counts.passed` 的含义随之改变。

> **口径补充（2026-10-08，卡 05 的真实运行暴露后修订）**（决策全文与理由见 ADR-011）
>
> 本节此前把 `evidenceQuote` 只当作**确定性判据的输入**，第 2 层的提示词也据此把它定义成
> 「逐字复制的一段文字，不超过 120 字」——它回答的是「**模型有没有编**」。
> 而判定者判据问的是同一字段上的**第二个、不同的问题**：「**这段引文是否支撑这条主张**」。
> 该字段从未为此被规定过，于是判定者接入后的第一次真实运行即暴露缺口：
> 37 个对象里 12 个（32.4%）被判「不充分」，且**全是同一个模式**——主张断言得比引文更多，
> 而主张里的断言其实都在锚点原文里，只是引文没选在支撑它的那几段。
> 拒绝率随主张承载的断言数单调上升（`EngineeringRule` 0% → `AntiPattern` / `MentalModel` 100%）。
>
> 现定为：**`evidenceQuote` 同时承担两个用途，二者必须同时成立。**
>
> 1. **防编造凭证**：连续、逐字的原文片段，在锚点区间内逐字命中（原判据不变）。
> 2. **语义证据**：主张里的每一条断言都要能从它里面读出来；**主张不得断言引文之外的内容**，
>    包括限定与范围。短引文不足以承载主张时，二选一——把引文写长到能承载，或把主张收窄到
>    引文能承载的粒度。
>
> 长度上限（现为 400 字）**放在提示词侧**，不进 schema、也不做机器判据：上限是调参，
> 契约不该随调参漂移。schema 只保留 `minLength: 1`。
>
> 引用本节实测数字时须注明是**单章单次运行**的结果，不得写成全书的普遍比例。

### D7 · 回执的形状与拒绝理由码

回执至少含：运行标识、源文件哈希、三段的产物指针与计数、逐对象的判定明细、拒绝项及其理由码、判定者实例标识、第 2 层调用与 token 用量。

拒绝理由码需至少能区分以下五类，因为它们的修复责任方不同：

| 理由码类别 | 责任方与修复动作 |
|---|---|
| schema 不合规 | 第 2 层提示词/输出契约 |
| 标识符或锚点不可解析 | 第 1 层锚点索引 |
| 源版本已变更 | 重跑第 1 层或重跑第 2 层 |
| 引文未逐字命中 | 第 2 层（最可能是归纳时改写了原文） |
| 判定者判为不支撑 | 第 2 层输入组织方式（引文与主张无关或相矛盾——引文选错了） |
| 判定者判为不充分 | 锚点切分（证据不足）或第 2 层（主张写得比证据宽） |

> **口径补充（2026-10-08，卡 05 期间）**：上表末两行是卡 05 拆出的。规格原文只列了
> 「判定者判为不支撑」一行，但判定者是三值输出，而「不充分」的修复方与「不支撑」不同：
> 前者要动锚点切分或把主张写窄，后者要重选引文。按 ADR-006 的口径，理由码的可区分性
> 正是 R6（验证过严、误杀有效对象）能否被检测的前提，因此两者分列。
> 封闭词表见 `pipeline/tools/verifier.mjs` 的 `REASON_CODES`；回执里的
> `reasonCodes.vocabulary` 从该真源生成，不另抄一份。

理由码的可区分性是方案 R6（验证过严、误杀有效对象）能否被检测的前提——拒绝率高但无法归因时，人只能靠通读判断。

### D8 · 退出码语义

- `0`：全部对象通过第 3 层。
- 非 `0` 且可区分为**「有对象被拒」**（流水线本身成功执行）。
- 非 `0` 且可区分为**「运行失败」**（源文件不存在、锚点索引无法产出、第 2 层调用失败等）。

两类必须可区分：前者是**内容问题**（预期会发生，需要人看回执），后者是**工程问题**（需要修代码）。混成一个非零码会让 CI 无法区分「这本书抽得不好」与「脚本坏了」。

### D9 · 平面隔离与污染隔离的实现方式

- 第 1 层只读 `sources/` 下的源文件；第 2、3 层只读第 1 层产物。
- 中间产物写 `pipeline/knowledge/`，回执写 `pipeline/registry/`；`skills/` 本规格**完全不写**（它只接收门禁全通过的成品）。
- **盲测基准目录的隔离必须写进代码**：链路任一环节的输入路径解析不得接受基准目录路径；隔离失效会使 ADR-001 的对照前提整体作废（方案 R4）。

### D10 · 对象标识的确定性生成

同一个锚点 + 同一个对象序号 → 同一个对象 `id`。理由：重跑不产生重复对象；下游可按 id 稳定引用；同一对象被替换时靠 `revision` / `supersedes` 表达而非改 id。

### D11 · 第 2 层输入的两种组织方式

- **常规提取**：按章节顺序喂入，产出以原文有明确载体的对象（`Concept` / `Metric` / `Playbook` / `Case` 等）。
- **跨章综合**：`AntiPattern` **必须按主题组织输入，而非按章节**。这是 ADR-005 的显式要求，也是本规格中唯一一处「输入组织方式本身是设计决策」的地方。

反模式的跨章依据（实测）：全书「常见陷阱」字面 0 命中；显式失败小节 13 处，分布 chapter10 共 7、chapter5 共 1、chapter7 共 3、chapter8 共 2，其余章节 0。而目标量级是 22 个 skill × 6–8 条 ≈ 130–176 条。这个差距不是「抽得不够努力」，是**必须综合**。

### D12 · 语言与工具链

- 实现语言与运行时：采用**本机已实测可用的工具链**，不引入需要网络安装的运行时依赖（ADR-005 已否决把外部提取引擎作为主干依赖）。
- 实测可用：`node v26.7.0`、`python3 3.14.7`、`jq 1.7.1`、`git 2.50.1`（命令与版本见「核实方式」）。
- schema 以 **JSON Schema** 表达，使第 3 层能直接调用通用校验而非自写字段检查。

## 测试决策

### 什么算好测试

只测**外部行为**：命令的输入、落盘产物、回执内容、退出码。不测内部函数、不测中间变量、不断言实现结构。

判定标准：一个测试如果在重构内部实现后必然失败，它测的就是实现细节，不合格。

### 哪些模块将被测

| 对象 | 测什么 | 为什么它值得测 |
|---|---|---|
| 第 1 层结构层 | 锚点数量、行号区间、稳定性（同一输入两次运行产出逐字节相同） | 它是全链路可溯源的底座，且确定性使它可以被严格断言 |
| 第 1 层锚点解析 | 非规范标题（中文、全角冒号、`{.unnumbered}` 标记）能被正确解析 | 实测原文就是这么写的，假定纯 ASCII 会漏 |
| 第 3 层确定性判据 | 逐字比对、schema 校验、锚点可解析、源版本哈希一致性 | 门禁一的主力；它误判会使好对象被系统性误杀 |
| 第 3 层退出码 | 「有对象被拒」与「运行失败」可区分 | CI 集成的前提 |
| 端到端 | 对一个小源文件跑完整命令，产物与回执齐备、退出码正确 | 这是本规格唯一真正的验收面 |

### 测试的先行范例

**范例一（正向/负向 fixture 配对）**：Kb2Agent 采用 `reference/fixtures/positive/` 与 `reference/fixtures/negative/` 配对的契约测试，其反例 fixture 打的正是「公开面只能到 E2」这一硬约束点。本规格沿用该形态：为每种对象类型备**一个正例与至少一个负例**，负例针对该类型最容易被违反的必填字段。

**范例二（一个正例包 + 固定负例集 + 跨对象不变量）**：Kb2Agent 的契约验收脚本的验收口径为「一个正例包、六个固定负例和跨对象不变量」。本规格的第 1、3 层测试沿用这一口径。

⚠️ **未核实说明**：上述两个范例的**形态**来自对 Kb2Agent 仓库脚本源码与验收文件的阅读（见 `analysis/05-source-analysis.md` 第 37、46 行）。该仓库**从未被实际运行**——其 `npm run reference:contracts` 需要 `node_modules`，本项目未安装，因此**没有运行回执**。引用其形态可以，**不得**声称「其测试已通过」或复述其结果。

## 范围之外

以下事项**明确不在本规格内**：

1. **环 3 语义聚类**：内容单元划分、`SkillCandidate` 产出、聚类依据记录。属 ADR-007 的范围。
2. **环 4 skill 构建**：`skills/<name>/SKILL.md` 的生成、6 段骨架、frontmatter 硬限制、体积阈值与溢出阀。属 ADR-004 的范围。
3. **环 5 门禁二与门禁三**：触发盲测（盲测 agent）、效用 A/B（消费者 agent）、晋升回执。属 ADR-006 的范围；本规格只交付**门禁一**。
4. **盲测基准比对**：与 22 个基准 skill 的数量与覆盖对照。属 ADR-001 的范围。
5. **效用评估的负迁移检测**：本规格不测效用，只保证原料可信。
6. **多源输入**：本规格只处理单一内容源文件；「任意内容源」这一更大目标是本项目的长期方向，MVP 首轮只处理本书中文正文。
7. **契约侧车**（`inputContract` / `outputContract` / `tools` / `steps` / `stopConditions` / `rollback` / `tests` 等）：属 ADR-004，且它以 skill 为承载单位，本规格尚未产出 skill。
8. **按主题组织输入的提示词工程细节**：属实现，不在规格层锁定。
9. **第 2 层模型选型**：规格局部不指定具体模型；但要求其调用与用量须被回执记录（D7）。

### 本规格新增、上游未规定的决策

以下 5 条是本规格新引入的，需要用户知晓：

1. **逐字引文（`evidenceQuote`）作为第 2 层的强制产出**——上游只要求 `sourceRefs` 指向位置。本规格把「引文逐字命中」提升为主力确定性判据，因此要求对象携带引文本身。代价：第 2 层产出体积增加；收益：验证从主观变机械。
2. **锚点标识不含行号**——稳定性优先于可读性。
3. **退出码二分类**（内容问题 / 工程问题）。
4. **对象 `id` 由锚点确定生成**——重跑不产生重复对象。
5. **判定者判据与确定性判据同权**（两组均须通过）。
