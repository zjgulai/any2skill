## 2. 主线任务：修 `layer2-response`，再跑一次全书

> ⚠ **本节已于 2026-10-12 被 ADR-023 更正**：下面这段「症状—根因」的描述中，
> **根因那一半是错的**。真实根因见本节末尾的更正块。

### 症状

首跑 `book-07faf309c5a1`（2026-10-11 20:47:49 → 22:18:10 CST，**墙钟 90.4 分钟**）13 个文件里 **6 个退出码 4**，
失败种类**全部**是 `layer2-response`：

| 文件 | 报错片段（`run-failed-*.receipt.json` 的 `engineeringFailure.message`） |
|---|---|
| chapter3 | `Unexpected token 'e', "text\nExtra"... is not valid JSON` |
| chapter10 | `Unexpected token 'p', "python\nwo"...` |
| chapter2 | `Unexpected token 'e', "text\n# 工具使"...` |
| chapter7 | `Unexpected token 'e', "text\n文件原始字"...` |
| introduction | `Unexpected token 'b', "bash\ngit "...` |
| chapter6 | `Unexpected token 'e', "text\n桌面状态 "...` |

六个前缀 `text` / `python` / `bash` **都是 markdown 代码围栏的语言标签**。

### ⚠ 更正：根因不是「模型写坏」，是解析器切坏

本节原文断言「模型把裸换行写进了字符串」。**复现证伪**：

```bash
cd /Users/lute/Project/any2skills
node -e '
const fs=require("fs");
fs.readdirSync("pipeline/registry")
  .filter(x=>x.startsWith("run-failed-")&&x.endsWith(".layer2-raw.json"))
  .forEach(f=>{
    const t=JSON.parse(fs.readFileSync("pipeline/registry/"+f,"utf8")).rawText;
    try{JSON.parse(t);console.log("✅ 本身合法",f)}catch(e){console.log("❌ 本身不合法",f,e.message.slice(0,40))}
  });'
# → 6 份全部「本身合法」
```

旧 `parseModelPayload` 的围栏正则 `/```(?:json)?\s*([\s\S]*?)```/` **没有 `^` / `$` 锚定**。
技术书稿里几乎每个锚点都含代码块，于是 JSON 字符串**内部**必然出现一对 ```` ``` ````；
这个正则从响应头部一路匹配到字符串内那个围栏的结束符，把一大段中间内容当「围栏壳」剥掉，
剩下的残片以 `bash`（或 `text` / `python`）开头——**报错里那个首字母就是这么来的**。

同一份正则抄在**四个**解析器里（`layer2-extractor` / `judge` / `theme-proposer` /
`antipattern-synthesis`）。修复：提取 `pipeline/tools/model-json.mjs` 为唯一实现，
四种形态的判定顺序改为「整份原样 → **锚定**围栏 → 首 `{` 末 `}`」。
**提示词未改动，`PIPELINE_VERSION` 不变**，已完成的 7 个文件断点续跑不受影响。

**因此第 2 节下面的「三条候选路线」已不适用**——那三条都建立在「模型输出坏」的前提上，
而该前提不成立。保留原文仅为留痕。

### 旧分析的留痕（前提已证伪，仅供追溯）

三个环节叠加，每一环单独看都合理：

1. `pipeline/tools/llm-client.mjs`：重试**只覆盖**传输错误与 HTTP `429` / `5xx`
   （`const retriable = res.status === 429 || res.status >= 500`）。
   **200 + 坏 body 走不进重试。**
2. `pipeline/tools/layer2-extractor.mjs` 的 `parseModelPayload`：只做「去 markdown 围栏」与
   「取第一个 `{` 到最后一个 `}`」两种**壳层**容错，注释里明确写着「不做语义修补」，失败即抛 `Layer2Error`。
3. `pipeline/run.mjs`：该错误在文件级是**终止性**的——剩下的锚点不再推进。

失败率不低：13 个文件里有 6 个（46%）撞上，且这 6 个跨了不同长度、不同章节。

### ~~三条候选路线~~（已作废，见上面的更正）

| 路线 | 代价 |
|---|---|
| 解析层有限重试（重发那个锚点） | 要重新花钱，且不保证下一次就合法；好处是不动判据、不动内容 |
| 容错修补（转义字符串内的裸换行再 parse） | 有「静默改动内容」的风险，与该项目「不做语义修补」的既有立场**直接冲突**——若选这条，必须在回执里标记「这一条是靠修补救回来的」 |
| 改提示词要求转义 / 附 not-escaped 示例 | 提示词一变就要升 `PIPELINE_VERSION`（进运行指纹，旧回执与新回执必须身份可区分） |

> **作废理由**：三条都是「模型输出有问题」的解。真实根因是解析器，因此正确解法是**修解析器**
> ——不动提示词、不加重试、不做修补。已按此实施（ADR-023）。

### 好消息：重跑很便宜

第 2 层**断点续跑**已实现。已完成的锚点落在
`pipeline/registry/<file>.layer2-raw.partial.json`，下次运行自动从那里接着跑，
**失败的代价只限于当次在飞的那一个锚点**。所以修完之后重跑，只为**没跑完的锚点**付钱。

## 6. 两个必须先知道的事实陷阱

### 陷阱一：`totals.anchors = 138` 不是全书的锚点数

全书 13 个文件实测共 **336** 个锚点（逐文件复算 3+25+34+42+29+20+20+40+48+42+17+5+11）。
但 `aggregateTotals` 用的是 `sum(f => f.coverage?.indexAnchors)`，
而 6 个失败文件的 `coverage` 是 `null`——于是那个 138 只是**有 coverage 的 7 个文件**的和。
逐文件行如实显示 `—`，但顶层数字**没有任何伴随字段**说明「另有 198 个锚点无覆盖数据」。
`docs/tickets/09-full-book-run.md` 已把这条记为未决项。

### 陷阱二：`totals.model` 里混着回放的数字，且失败文件的花费根本不在里面

- chapter4 本次 **0 秒**完成，`judge.enabled=false`：它的 39 个对象、20 次调用、44,834/121,655 token
  **全部是回放上一轮回执**（同版本回执按身份重用，这是 ADR-014 的既定行为，不是 bug）。
  所以「今天真跑掉的调用」是 138 − 20 = **118**。
- 6 个失败文件各自的失败回执写着 `billing: "unknown（失败路径没有记账，不得读成 none）"`。
  它们白花的量可从 `partial` 的 `usageSoFar` 取回（**已完成**锚点的部分）：
  **85 次调用 / 178,138 输入 / 508,200 输出**。这是**下界**——
  把文件打死的那个调用自身没被记账（推算，推导链：每个失败文件至少一次未计入的调用，故真实值 ≥ 91）。
- 另外：256 条「通过 253」里，**39 条是回放的**，本次判定者没看过。
  引用这个数时必须带上这一句。

## 7. 别做的事

- **别把 `--layer2 stub` 加到真实产物上。** 它**不检查已有产出**，会直接用替身对象覆写
  `pipeline/knowledge/<file>.objects.json`（旧的一份归档进 `history/`，可恢复但你会先拿到假产出）。
  这条已实测踩到过，README「运行」章有醒目警告。
- **别用 `cmd | tee log` 读退出码。** 管道只保留最后一环的退出码，一次真崩溃会被报成 `exit 0`。
  要么 `set -o pipefail`，要么不接管道。
- **别在未跑完 `--verify-isolation` 时宣称「隔离通过」。** 聚合回执里的 `isolation.children`
  只是子进程账本的**当时快照**；编排进程自己的账本在进程退出时才落盘，最终结论必须跑那条命令取。
- **别把 `EXIT_LEDGER_MISSING = 4` 当成一个独立的退出码。** `pipeline/run-book.mjs:58` 导出了它，
  但**全文件再无引用**（实测 `grep -n EXIT_LEDGER_MISSING pipeline/run-book.mjs` 只命中第 58 行）。
  退出码 4 的真源是 `run.mjs` 的 `EXIT.RUN_FAILED`。这是本轮留下的一个死导出，顺手清掉即可。
