# ADR-012 · 判定者看到的「主张」= 断言 + 适用范围

- 状态：已接受
- 日期：2026-10-08
- 决策者：用户（在「逐类型纳入范围字段 / 维持只取断言字段 / 一条统一规则全量纳入」三选项中拍板第一项）
- 关联：ADR-010（判定者设计）、ADR-011（引文的职责，其更正块提出本问题）；规格 `docs/specs/01-pipeline-spec.md` 的 D6
- 落地任务卡：`docs/tickets/05-verifier-independence.md`

## 背景

ADR-011 决定「引文必须支撑主张」之后，紧接着暴露了一个它没覆盖的问题：
**判定者看到的「主张」到底包含哪些字段？**

反证来自修复验证跑 `run-470138ece6a3`——修复后仍被拒的 1 条（判定者类）是
`CHAPTER4-H4-2-HEURISTIC-02`：

| 字段 | 内容 |
|---|---|
| `trigger` | 「当需要处理**文本内容占主体的 PDF 文档等**，并在提取为文本与转换为图片的原生多模态处理之间选择时」 |
| `recommendation` | 「选择提取为文本的方法，而不是转换为图片的原生多模态处理方法，因为往往更节约 token。」 |
| 判定者理由 | 「引文仅限定于『文本内容占主体的 PDF 文档等』场景下……而**主张未加该限定**，断言得更宽泛。」 |

**限定词在对象上，只是不在判定者看得到的那几个字段里。** 当时 `CLAIM_FIELDS.Heuristic`
只取了 `recommendation`，于是判定者看到一条**无界**的推荐，并（正确地）判定它不被引文支撑。

**不完整是我们造成的，不是对象的问题。** 用一个自己造出来的不完整主张去否定对象，
是这道门禁最不该犯的错——它的全部信誉建立在「判得准」上。

对照同类型通过的 `CHAPTER4-H3-1-HEURISTIC-01`：它的 `recommendation` **把限定词写在了句子里**
（「当存在明确的安全、权限或性能理由时，可以偏离此默认取向」），因此不依赖 `trigger` 也站得住。
⇒ 这解释了为什么该问题只在**部分**对象上显形：能否站得住取决于模型把限定词写进了哪个字段，
而那是一次采样，不是一条规则。

### 一次必须留痕的更正

ADR-011 曾写下「把那些未进主张的字段加进去**只会让主张更大**，单条引文更难支撑」，
并据此排除该解释。**该判断对断言承载类字段成立，对范围限定类字段恰恰相反**——
后者加进去会让主张**更窄、更精确**，从而**更容易**被支撑。
该更正已记在 ADR-011 的更正块内，此处不重复，仅记其结论。

## 决策

**范围限定类字段一律进主张，逐类型列举，不用一条统一规则。**

| 类型 | 纳入的范围字段 | 判定者看到的主张 |
|---|---|---|
| `Metric` | `window` | 窗口 + 名称 + 公式 |
| `MentalModel` | `trigger` | 触发条件 + 推理 |
| `Heuristic` | `trigger` | 触发条件 + 建议 |
| `EngineeringRule` | `appliesWhen` | 适用条件 + 陈述 |

书写顺序是**范围在前、断言在后**，使主张读起来就是「在什么情况下、主张什么」。

## 为什么逐类型列举，而不是一条统一规则

统一规则（「除叙述类外全部字段进主张」）会顺带拖进 `DecisionModel.inputs`、
`Playbook.prerequisites`、`unknownPolicy`、`stopConditions` 这些**不是范围而是新断言**的字段，
使主张变大、判定变严——那是与本次修正**方向相反**的错，而且它会把拒绝率推向另一个方向。

反过来，逐类型判断要回答的是「这个字段是**限定**还是**新的断言**」，而这个问题在几种字段上
确实没有统一答案：

| 字段 | 判断 | 理由 |
|---|---|---|
| `Heuristic.trigger` / `MentalModel.trigger` | **是限定** | 抽掉它，建议/推理会读成无条件成立 |
| `EngineeringRule.appliesWhen` | **是限定** | 同上 |
| `Metric.window` | **是限定** | 抽掉它，公式的计量口径不确定，断言本身就不完整 |
| `DecisionModel.inputs` | **不是** | 声明输入是什么；分支条件本身已在 `branches` 里 |
| `Case.context` | **不是** | 一段叙述（背景交代），不构成适用范围 |
| `Playbook.prerequisites` | **不是** | 描述执行前提，不描述「这套流程在什么情况下成立」 |
| `examples` / `aliases` / `evidence` | **不是** | 断言的展开；并进去会让主张变大（反向的错） |
| `limits` / `counterexample` / `exceptions` | **不是** | 边界的展开说明 |

这张表就是决策的实体。它随代码存放在 `pipeline/tools/object-contract.mjs` 的 `CLAIM_FIELDS`
文档注释里，并由 `judge-verdict.test.mjs` 的「主张 = 断言 + 适用范围」一节逐条钉住
（含一份**明确不进**清单，防止后来者把 `context` / `inputs` 当成漏掉的适用范围又加回来）。

## 修复验证（实测）

用 `--judge` 对**同一批已落盘对象**重扫判定者——这一步之所以只花 33 次判定调用而不必重跑第 2 层，
正是因为本次改动只动了「判定者看到的主张」，没动提取。判据版本由 v4 提到 v5，使重判路径被触发。

| | 改动前（主张只含断言） | 改动后（主张含适用范围） |
|---|---|---|
| 判定者调用 | 33 | 33 |
| 支撑 | 32 | **33** |
| 不充分 | **1** | **0** |
| 判定者 token | input 44,666 / output 6,716 | input 45,082 / output 7,906 |

反证对象 `CHAPTER4-H4-2-HEURISTIC-02` 的判定者理由，前后对比：

- **改动前**：「引文仅限定于『文本内容占主体的 PDF 文档等』场景下……而**主张未加该限定**，断言得更宽泛。」
- **改动后**：「引文明确说明**对于文本占主体的 PDF**，提取为文本比转换为图片更节约 token，
  **直接支持该选择建议**。」

同一段引文、同一个对象、同一个判定值域——变的只是判定者**能看到哪几个字段**。
这是对本 ADR 诊断最直接的验证：问题从来不在对象，也不在引文，而在我们递给判定者的那半句话。

### 必须同时说清的边界：这一章现在**零判定者类拒绝**

33 个对象全部判「支撑」，1 个对象因 `QUOTE_MISMATCH` 被确定性判据拒（真缺陷：引文跨行拼接时
夹进了原文没有的字符）。**「全部通过」在这一个样本上无法与「橡皮图章」区分开。**
不得据此宣称判定者有效——本章能证明的是它**曾经**抓出 12 条引文不承载主张的系统性问题，
那是确定性判据完全看不见的；不能证明的是它在该样本上仍有区分力（样本里已经没有它要抓的东西了）。

见 ADR-010 与本卡工单里关于「不支撑」路径从未在真实数据上触发过的同一条纪律。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 维持现状，只取断言类字段 | 影响面当时只有 34 个里的 1 个（3%），看似可忽略。但等于把「限定词要写进断言字段」这条**提取规范**隐式地压在模型身上：它写不写是一次采样，不写就被判不充分。这会让拒绝率带上一层**与内容质量无关的噪声**，而噪声正是建这道门禁要消掉的东西。 |
| 一条统一规则全量纳入（除叙述类外） | 会拖进 `inputs` / `prerequisites` / `unknownPolicy` / `stopConditions` 等新断言字段，使主张变大、判定变严——与本次修正方向相反，且会把拒绝率推向另一个方向。 |

## 后果

**正面**
- 判定者看到的是**对象实际断言的东西**，而不是我们抽掉范围后剩下的半句话。
- 拒绝率不再混杂「模型把限定词写在了哪个字段」这种采样噪声。

**负面 / 代价**
- `CLAIM_FIELDS` 从此是一张需要维护的表：新增对象类型或新增范围类字段时必须同步判断。
  缓解手段是上面那张「是/不是限定」的判断表 + 双向测试（该进的进、该不进的不得进）。
- 判定者输入变大（多了 1 个字段），但相对锚点原文（本章实测单个锚点可达 3,000+ 字符）可忽略。

**必须遵守的约束**
- 范围类字段**必须逐类型判断**，不得用一条统一规则代替。
- 「明确不进」清单**不得删**——它是防止同类错误反向重演的唯一凭据。
- `CLAIM_FIELDS` 的变更属于**判定口径变更**，必须同时递增 `PIPELINE_VERSION`，
  否则重判路径不会触发，旧回执记的计数会继续冒充现状。
