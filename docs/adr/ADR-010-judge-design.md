# ADR-010 · 第 3 层判定者：同模型独立实例、三值语义、默认短路

- 状态：已接受
- 日期：2026-10-08
- 决策者：用户（就模型路由、`不充分` 语义、调用范围三处分别拍板，均为推荐项）
- 关联：ADR-005（第 3 层独立于第 2 层）、ADR-006（门禁一不得自评）、ADR-009；规格 `docs/specs/01-pipeline-spec.md` 的 D6 / D7
- 落地任务卡：`docs/tickets/05-verifier-independence.md`

## 背景

规格 D6 把第 3 层拆成**确定性判据**与**判定者判据**，并要求判定者与生产者「不同实例、不同上下文」，
输入中不含生产者的推理过程与提示词。卡 03 只交付了确定性判据（`checkDeterministic`），
并把判定者留成桩：

```bash
grep -n "export function judge" -A14 pipeline/tools/verifier.mjs
# → 返回 verdict: 'not-implemented'；已带 FORBIDDEN_JUDGE_CONTEXT_KEYS 守卫
```

卡 05 的活是把桩换成真实调用，并把「隔离」从注释变成**可被测试证明的事实**。

规格 D6 只写明了三值输出中的两件事：输出「支撑 / 不支撑 / 不充分 + 一句理由」，
以及「判定为**不支撑**时必须拒绝，不得仅标注」。**「不充分」算过还是算拒，规格没写**——
这是本轮必须由用户拍板的第一处口径歧义。

### 两条已核实的原文（本轮 `sed` 实测，ADR-006 引用）

- `chapter3.md:524`：「**两个 Agent 应优先使用能力相近但来自不同家族的模型。**……不同的训练数据、
  偏好和推理习惯可降低两者在同一处犯同类错误的概率；能力则不宜悬殊」
- `chapter4.md:308`：「关键在于审查对象不同——提议者-审核者审查的是**开放式思考**，
  因此需要能力相近的模型；Sidecar 判断的则是较简单的分类问题，轻量模型足以胜任」

### 一处必须留痕的张力

`chapter3.md:524` 同一段还写着：「**Proposer 和 Reviewer 都必须是 Agent，而不是两次固定的 LLM API 调用。**」
而卡 05 明确要求判定者是**输入受限的固定调用**。两者不矛盾，但口径不同：

- 那段讲的是**知识库 PR 审核**，Reviewer 需要自己去搜证据、比版本、跑检查，所以必须是 Agent；
- 本卡的判定者是**门禁的一环**，其输入受限正是为了堵住「沿生产者的结论再讲一遍」与推理回流，
  因此必须是受限调用。

⇒ 这是**同一原则在不同环节的不同落实**，不是自相矛盾。记于此，避免后来者据 chapter3 推翻本卡设计。

## 决策

### 1. 判定者模型路由：同模型、独立实例，且路由独立可配

- 判定者与生产者**同模型**（`deepseek-v4-pro`），但**独立配置**——判定者路由从环境变量单列解析，
  不与第 2 层共用，使「换判定者模型」退化成一次配置改动而非重写。
- 独立性由**代码结构**保证，不由模型名保证。
- 理由：规格 D6 的硬约束是「不同实例、不同上下文」，这半边**能被代码证明**（本卡的哨兵测试证明的正是它）；
  「不同家族」是降低同类错误的**概率手段**，无法被测试证明，只能靠统计。先把可证明的那半做扎实，
  等有了真实的支撑/不充分/不支撑分布，再用数据决定要不要换——那时有证据，现在没有。
- 端点实测（只读 `GET /models` → HTTP 200）只有两个档位：`deepseek-flash`、`deepseek-v4-pro`。
  ⇒ 「不同家族」必须引入第二条 provider 路由与第二个凭据，不是换个模型名的事。
- **代价与缓解**：MVP 阶段同家族共享盲区不设防。缓解办法是回执**记录判定者的 modelId 与 instanceId**，
  使「同模型自审」这件事在审计时看得见，而不是隐形的。

### 2. 三值语义：只有「支撑」算通过

| 判定者输出 | 判定 | 理由码 | 修复责任方 |
|---|---|---|---|
| 支撑 | 通过 | — | — |
| 不支撑 | **拒绝** | `JUDGE_NOT_SUPPORTED` | 第 2 层输入组织方式 |
| 不充分 | **拒绝** | `JUDGE_INSUFFICIENT` | 锚点切分（证据不足）或主张写得比证据宽 |

- 理由：卡 05 原文写的是「两组均须通过」，而不充分显然不是通过；fail-closed 与 ADR-006 的
  「不通过即拒绝、无豁免」一致。
- 保留三值区分的**诊断价值**：不支撑意味着引文与主张**矛盾**（修法：第 2 层改写），
  不充分意味着**证据不够**（修法：锚点切分太碎，或主张写得比证据宽）。两件事的修法不同，
  混成一个码会让 D7 的可归因性失效——那正是 ADR-006 说要靠理由码区分来检测 R6 的前提。

### 3. 调用范围：默认短路，另留显式开关跑全量对照

- **常规路径**：只对**已通过确定性判据**的对象调用判定者。已被确定性判据拒绝的对象在回执里
  写明「未送判定，已被确定性判据拒绝」，使「没看过」与「看过但没判」可区分。
- **显式开关** `--judge-all`：所有对象都送判定者，产出
  `{确定性通过/拒绝} × {支撑/不充分/不支撑}` 的交叉表。
- 理由：短路保护的是**迭代回路**——提示词没调好、拒率飙到 50% 时，全量会几乎把成本翻倍，
  而那正是跑得最勤的时候。同时把「两组判据对不对得上」这个证据跑出来一次，不靠推测。
- 全量模式下，对「引文根本不在锚点内」的对象，判定者看到的引文与锚点文本本就对不上，
  它给出的「支撑」是**范畴混淆**而非有效交叉验证——交叉表解读时必须按拒绝理由分列看。

### 4. 判定者理由码在优先级中的位置：末位

`REASON_PRECEDENCE` 追加 `JUDGE_INSUFFICIENT`、`JUDGE_NOT_SUPPORTED` 于**末位**（`QUOTE_MISMATCH` 之后）。

理由：判定者的判定以「引文存在且可定位」为前提。引文没命中锚点时，判定者根本没有可判的对象，
此时若把判定者码排在前面，会把「出处对不上」误报成「判定者不认」，两者的修复方不同。

## 附带发现与处置：`temperature` 在思考模式下静默失效

DeepSeek 官方文档明确：「思考模式不支持 `temperature`、`presence_penalty`、`frequency_penalty` 参数。
请注意，为了兼容已有软件，**设置参数不会报错，但也不会生效**。」

而本流水线代码里 `DEFAULT_TEMPERATURE = 0`，一路传进请求体——**它一次都没生效过**。

- 性质：这不是缺陷（本流水线从未据它宣称确定性；规格明文说第 2 层是非确定性的，确定性只承诺给第 3 层的确定性判据），
  但它是一个**认知陷阱**：后来者读到 `temperature: 0` 会以为生成是确定性的。
- 处置：**保留参数但消除陷阱**——在定义处写明「思考模式下不生效」并给出官方出处；
  回执的 model 块记录 `temperatureEffective: false`（当思考模式开启时），使「我们以为在控制、其实没控制」
  这件事在回执里看得见，不必翻代码也不必记住。
- 不做的处置：不删除该参数。它在思考模式被关闭时重新有意义（ADR-009 的档位决策正会动这一片）。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 判定者用不同家族模型（引入第二条 provider 路由） | 对齐 chapter3.md:524 原文，但需第二条路由 + 第二个凭据 + 两套供应商错误模式；判定者调用量按 chapter4 实测 38 次/章、全书推算约 640 次，双路由的运维面在 MVP 阶段先于收益到位。留成配置口子，等有数据再换。 |
| 判定者用同端点轻量档 `deepseek-flash` | chapter4.md:308 说审查对象决定能力要求，看似支持；但同段紧接着就是「能力则不宜悬殊，否则 Reviewer 可能根本跟不上」，而本卡判定的是开放式主张而非命令分类。轻量判定者最可能的失败是**被生产者的措辞说服**（把橡皮图章从结构问题换成能力问题），且这种失败**判据看不见**——它会给出「支撑」。 |
| 「不充分」放行，仅在回执标注 | 与同一条验收里的「两组均须通过」相冲；且判定者最容易被卡住的灰色地带恰恰是「引文有点相关但不完全支持」，放行等于把门禁松紧交给模型的措辞习惯。 |
| 「不充分」打成待人工裁定队列 | 与卡 09 的硬要求「单次运行完成、不可交互式确认」相冲；全书推算约 640 次判定，人工队列会迅速变成新瓶颈。 |
| 全量判定（不开短路口子） | 拒率高的章节成本接近翻倍，且对引文不在锚点内的对象会产生范畴混淆的假信号。 |
| 只做短路、不开全量口子 | 永远拿不到两组判据的对照数据，而卡 05 的全部职责就是证明判定者真的独立。 |

## 后果

**正面**
- 隔离由「构造式输入」+ 哨兵测试共同保证：判定者输入是**构造**出来的三个叶子字段，
  不是从对象上删字段得来的——删除式隔离会被新增字段默默绕过。
- 判定者的 modelId 与 instanceId 进回执，「谁判的」可审计。
- 全量开关使「确定性判据与判定者判据对不对得上」可被实测，而不只是被断言。

**负面 / 代价**
- 同家族共享盲区在 MVP 阶段不设防（见决策 1 的缓解）。
- 短路使判定者只能否决幸存者，不能推翻确定性判据的拒绝。逻辑上与「两组均须通过」等价（合取满足短路求值），
  但**代价是**「确定性判据是否过严」无法由判定者交叉验证——检测 R6 仍需人工看 `quoteComparison`。

**必须遵守的约束**
- 判定者输入**只含**主张、逐字引文、对应锚点区间文本三样；不得传入对象其余字段。
- 判定者**不得**拿到生产者提示词、推理过程、完整输出历史、其他对象的产出。
- `不支撑` 与 `不充分` 均**必须拒绝**，不得仅标注。
- 回执必须记录判定者实例标识，否则「同模型自审」这件事在审计时不可见。
