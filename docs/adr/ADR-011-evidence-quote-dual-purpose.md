# ADR-011 · 引文的职责：既是防编造凭证，也是语义证据

- 状态：已接受
- 日期：2026-10-08
- 决策者：用户（在「改写第 2 层提示词并放宽上限 / 判定者改判锚点区间 / 维持现状」三选项中拍板第一项）
- 关联：ADR-005（三段式）、ADR-006（门禁一）、ADR-010（判定者设计）；规格 `docs/specs/01-pipeline-spec.md` 的 D4 / D6
- 落地任务卡：`docs/tickets/05-verifier-independence.md`（发现于本卡的真实运行）

## 背景：判定者接上的第一次真实运行，就量出了一条规格缺口

`run-7afb98d262b5`（chapter4，20 锚点，实测）：

| 项 | 值 |
|---|---|
| 对象 | 37 |
| 确定性判据通过 | **37 / 37**（引文全部逐字命中锚点区间） |
| 判定者判「支撑」 | 25 |
| 判定者判「不充分」 | **12**（32.4%） |
| 判定者判「不支撑」 | 0 |

⇒ **两组判据测的是两件事**：逐字比对对「引文与主张对不对得上」完全无感。这正是卡 05 存在的理由。

12 条「不充分」是**同一个结构性模式**，判定者给的理由高度一致：
引文支持主张的**一部分**，而主张还断言了引文里没有的内容。

**但是，主张里的每条断言都在锚点原文里。** 实测逐句核对 `CHAPTER4-H2-3-CONCEPT-01`：
主张说 MCP「是 Anthropic 于 2024 年底发布的开放标准……采用客户端-服务器架构，
并区分工具、资源与提示三类原语」，而它附的引文是「一个 MCP 服务器可以同时被
Cursor、Claude Desktop、OpenClaw 等任何兼容的客户端使用……」——断言全在原文，
只是**引文没选在支撑断言的那几段**。

### 根因：同一个字段被两个不同的问题使用过

第 2 层提示词原文（实测）：

> 「每个对象必须带 `evidenceQuote` 字段：从给定正文中**逐字复制**的一段文字（**不超过 120 字**）。
> 不得改写、不得拼接、不得翻译……第 3 层会把它与原文做**逐字比对**。」

它回答的是「**模型有没有编**」，为此设了 120 字上限。而判定者问的是
「**这段引文是否支撑这条主张**」——同一个字段上的**第二个、不同的问题**，而该字段从未为此被规定过。

**因此这不是第 2 层的执行缺陷，也不是模型不听话，而是卡 05 引入判定者时暴露的一条规格缺口。**

### 量化确认（实测，口径：引文与各字段的二元组字符重叠率；长度为归一化后字符数）

| 对象类型 | 主张字段 | 通过 | 不充分 | 拒绝率 |
|---|---|---|---|---|
| `EngineeringRule` | `statement`（单一断言） | 11 | 0 | **0%** |
| `Heuristic` | `recommendation` | 4 | 2 | 33% |
| `Concept` | `canonicalTerm` + `definition` | 10 | 6 | 38% |
| `AntiPattern` | `pattern` + `harm`（两条断言） | 0 | 3 | **100%** |
| `MentalModel` | `reasoning`（长段综合） | 0 | 1 | **100%** |

引文长度两组几乎相同（支撑组 59 字 / 不充分组 62 字），差异全在主张：
**主张/引文 长度比 = 支撑组 0.83、不充分组 1.23**。

⇒ 拒绝率随「主张要承载多少断言」**单调上升**。120 字引文上限是一个**固定预算**，
而主张可以无限宽——超出预算的部分必然无人承载。这是结构性错配，不是偶发缺陷。

**曾排除的替代解释（后经实测更正，见下方更正块）**：也曾怀疑是判定者的 `CLAIM_FIELDS` 选窄了
（把 `examples` 之类未进主张的字段纳入即可）。实测 12 条里只有 4 条的引文实际支撑的是未进主张的
字段，据此当时判定该解释不成立。

> ### ⚠️ 更正留痕（2026-10-08，本 ADR 定稿后，修复验证跑反证）
>
> **原文如此**：「把那些字段加进主张只会让主张更大，单条引文更难支撑。该解释被排除。」
> **实测为假，现已更正。** 该判断对**断言承载类**字段成立，对**范围限定类**字段**不成立**——
> 后者加进主张会让主张**更窄、更精确**，从而**更容易**被引文支撑。
>
> 反证来自修复验证跑 `run-470138ece6a3`：修复后仍被拒的仅 1 条（判定者类），
> 对象 `CHAPTER4-H4-2-HEURISTIC-02`：
>
> - `trigger`：**「当需要处理文本内容占主体的 PDF 文档等**，并在提取为文本与转换为图片的原生
>   多模态处理之间选择时」
> - `recommendation`：「选择提取为文本的方法，而不是转换为图片的原生多模态处理方法，
>   因为往往更节约 token。」——**限定词不在其中**
> - 判定者理由：「引文仅限定于『文本内容占主体的 PDF 文档等』场景下提取为文本更节约 token，
>   而主张未加该限定，断言得更宽泛。」
>
> **限定词在对象里，只是不在我为它选的那几个字段里。** 对照同类型通过的
> `CHAPTER4-H3-1-HEURISTIC-01`：它的 `recommendation` **把限定词写在了句子里**
> （「当存在明确的安全、权限或性能理由时，可以偏离此默认取向」），于是不依赖 `trigger` 也站得住。
>
> ⇒ 真正的规律是：**主张 = 断言 + 它的适用范围**。只用断言类字段、丢掉范围类字段，
> 会把一个本来有界的对象读成一个无界的断言，从而**误判为过度断言**。
> 影响面与处置方式（`CLAIM_FIELDS` 是否纳入范围类字段）另行拍板，见
> `docs/tickets/05-verifier-independence.md` 的待定项；本 ADR 的决策本身（引文须支撑主张）
> **不受影响**，受影响的只是「主张」一词的取值范围。

## 决策

**把「引文必须支撑主张」写进第 2 层提示词，同时放宽字数上限（120 → 400 字），
并把主张不得越界写成耦合要求。**

三处落地：

1. **提示词**（`pipeline/tools/layer2-extractor.mjs`）——新增两条**耦合**的硬性要求：
   - 引文必须是一个**连续**的原文片段，主张里的**每一条断言**都要能从它里面读出来；
   - 主张**不得断言引文之外的内容**，包括限定与范围（「总是」「唯一」「必须」，
     或某个特定适用场景）。
   并给出「短引文不足以承载主张」时的**二选一**：把引文写长到能承载，或把主张收窄到
   引文能承载的粒度。同时明确告知模型第 3 层有独立判定者会把关。
2. **契约描述**（`pipeline/schemas/knowledge-object.schema.json` 的 `$defs.quote`）——
   写明两个用途**必须同时成立**，并重新组装 9 份类型 schema。
3. **上限放在提示词侧，不进 schema**。理由见下。

## 为什么必须两条一起改

只放宽引文而不禁止主张越界，模型会把引文越写越长，直到引文≈锚点区间——那时「引文」
就不再是可供人一眼复核的要点，退化成了「把原文再抄一遍」。
只收窄主张而不放宽引文，对象会退化成单句断言，知识密度过低。

两条耦合起来，才得到一个稳定的中间态：**对象变窄、但每条都站得住**。
锚点可以多产出几个这样的对象（`maxObjectsPerAnchor` 可调），总信息量不必然下降。

## 为什么长度上限不进 schema

`schema` 是**契约**，`400` 是**调参**。上限会随判据口径调整，而契约不该随之漂移；
把可调数字写进契约，会让「同一份 schema」在两次调参之间产生不同的含义。
因此 schema 只写 `minLength: 1`，上限由提示词引导，且**不由机器判据强制**——
实测超长引文仍被接受（它仍逐字命中、仍在锚点区间内），交给判定者判断是否支撑主张。
`layer2-real.test.mjs` 的「05 · 引文的职责」一节把这几条逐项钉住。

## 修复验证（实测，单章单次运行）

改动后重跑同一章（`run-470138ece6a3`，`--rerun`）。两次运行的**判定者提示词指纹相同**
（`judge-90b1e1b49076`），第 2 层提示词指纹由 `prompt-f99d3ed8ead4` 变为 `prompt-22384598f992`
——因此唯一变量就是本次改动，对照是干净的。

| | 修改前 `run-7afb98d262b5` | 修改后 `run-470138ece6a3` |
|---|---|---|
| 对象数 | 37 | 34 |
| 通过 / 拒绝 | 25 / 12 | **32 / 2** |
| 拒绝率 | **32.4%** | **5.9%** |
| 判定者 支撑 / 不充分 | 25 / 12 | **32 / 1** |
| 引文长度（均值 / 中位数） | 60 / 51 字 | **169 / 150 字** |
| 主张长度（均值） | 58 字 | 61 字 |
| 主张 / 引文 长度比 | 0.96 | **0.36** |

（长度由归档对象集 `pipeline/knowledge/history/chapter4.a257afe6.objects.json` 与现行
`pipeline/knowledge/chapter4.objects.json` 复算；口径为归一化后字符数。核实方式见文末。）

**结论：修的是引文侧，不是主张侧。** 主张长度几乎没变（58 → 61 字），引文长度近三倍（60 → 169 字），
主张/引文比从 0.96 降到 0.36。这正是决策的预期形态——扩充证据，而不是阉割知识。

### 代价（实测）

| | 修改前 | 修改后 | 变化 |
|---|---|---|---|
| 第 2 层 input | 39,434 | 44,414 | +4,980（+12.6%） |
| 第 2 层 output | 82,318 | 121,219 | **+38,901（+47.3%）** |
| 判定者 input | 46,731 | 44,666 | −2,065 |
| 判定者 output | 16,126 | 6,716 | −9,410 |
| **两层 output 合计** | 98,444 | 127,935 | **+29,491（+30.0%）** |

⇒ 单章多花约三成输出 token，换回 26.5 个百分点的拒绝率。判定者一侧反而更省（争辩变少了）。
这笔账要带进 ADR-009 的定档评估：**提示词口径与推理档位是同一个成本函数上的两个旋钮。**

### 剩下 2 条拒绝各有各的原因，都不是本次决策能解决的

- `CHAPTER4-H2-7-ENGINEERINGRULE-01` → `QUOTE_MISMATCH`：引文跨行拼接时夹进了原文没有的
  排版字符，逐字比对不命中。这是**真缺陷**，判据正常工作。
- `CHAPTER4-H4-2-HEURISTIC-02` → `JUDGE_INSUFFICIENT`：即上文更正块里的范围限定问题，
  属「主张」取值范围的问题，不是引文职责的问题。

## 被否决的方案

| 方案 | 否决理由 |
|---|---|
| 判定者改判「锚点区间」而非「引文」 | 分工上确实更干净（`sourceRefs` 已用 `lineStart`/`lineEnd` 声明了证据区间）。但规格 D6 与卡 05 的验收项都明写「该引文是否支撑该对象的主张」，改判需同时改两处原文；且门禁会显著变松（本章大概率不再拒任何对象），这个变化**必须靠原理而不是靠数字来辩护**——否则很容易被读成「为了让数字好看而放宽判据」，而那是本项目最不能接受的失败模式。 |
| 维持现状，把 32.4% 当已知质量水位带进 06/07/09 | 全书跑批会按一个**未定义的证据口径**消耗预算；且拒绝非随机——拒绝率按类型从 0% 到 100% 分层，等于**按类型系统性丢弃**，丢的恰是断言最丰富的那几类（`AntiPattern`、`MentalModel`）。 |

## 后果

**正面**
- 引文的两个用途合一：一条引文既是防编造凭证，也是人复核这条主张时所看的那一段。
- 判定者的判据从此有明确的被判定对象——此前它在用第二个问题考一个为第一个问题设计的字段。
- 判定率从「结构性偏低」变为对提取质量的真实度量：**能通过 = 主张确实被它附的那段原文立住了**。

**负面 / 代价**
- 需重跑第 2 层验证（每章 20 次调用）。
- 单对象知识密度下降。缓解手段是提高单锚点对象数上限，而不是放宽证据要求。
- 提示词变长（新增约 8 行）。第 2 层的输入 token 会小幅上升；相对输出侧（本章实测
  output 82,318 / input 39,434），这点增量可忽略。

**必须遵守的约束**
- 引文与主张的耦合要求**不得只留一半**。测试逐条钉住两半都在。
- 长度上限**不得**写进 schema，也**不得**变成机器判据——它是一次调参，不是一个契约。
- 引用本次实测数字时，须注明是**单章单次运行**的结果，不得写成全书的普遍比例。

## 附带暴露的相邻问题（本 ADR 不决策，另案处理）

`promptFingerprint` 已进回执，但**复用/重判路径不拿它做任何判断**——实测
`pipeline/run.mjs` 的冻结复用只由 `checkFrozenFreshness`（源版本哈希）把关。
后果：**改了第 2 层提示词之后，一次普通重跑会静默复用旧提示词产出的对象，而回执里
那两个不同的指纹没有任何机制去对比。** 本次改动正是触发场景。
该问题的处理方式（拒绝复用 / 告警后复用 / 仅记录）需另行拍板，见
`docs/tickets/05-verifier-independence.md` 的待定项。
