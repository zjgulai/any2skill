# 07：单整章批量提取

**要构建什么：**把流水线从「一个章节的少量对象」扩到「一个**整章**的完整提取」——一次运行产出一个章节应得的**全部**对象，中间产物可增量落盘，使后续任务能直接消费而不必重跑。

本卡要解决的是规模问题：章节最大的两章实测为 `chapter2.md` 130,806 字节 / 11 个 `##`（含 KV Cache、提示工程、动态提示词与 Skills、Agent 状态栏、上下文压缩五块独立主题）与 `chapter8.md` 136,717 字节 / 17 个 `##`。这个体量下必须切分处理，而切分方式必须不破坏溯源。

**被谁阻塞：**04、06（反模式跨章综合须先成形，否则整章跑出的反模式质量无意义）

**状态：✅ 已完成（2026-10-09）**

- [x] 单章一次运行产出一个章节的**全部**对象，而非仅一二个样本
- [x] 超出单次输入预算的章节被**切分处理**，切分按小节/主题边界，**不按字节数硬切**
- [x] 切分后每个对象的 `sourceRefs` 仍可解析到 01 的锚点（切分不得破坏溯源）
- [x] 同章内产出多种对象类型，且类型分布写入回执
- [x] 中间产物**可增量落盘**：运行中断后重跑须**复用**已落盘的中间产物，而不是从零重算

- [x] 测试：中断后重跑，断言未重复产出既有对象
- [x] 对象 `id` 在同章多次运行间保持稳定（同一锚点 + 同一序号 → 同一 id）
- [x] 第 2 层用量（调用次数、token）按章可统计
- [x] 对 `chapter4.md`（71,664 字节 / 9 个 `##` / 7 个 `###`）跑整章，断言 9 个二级锚点全部被覆盖到 —— 即没有整节被静默跳过（**措辞已更正，见下**）
- [x] 测试：断言「已处理锚点数 = 索引中的锚点数」，以机械方式排除静默漏节
- [x] **回执必须能报出「被处理但产出 0 个对象」的锚点**：给出其计数与锚点清单，作为可复算的固定字段（**不是**仅存在于 `perAnchor` 明细里要靠人翻的一条 `objectCount: 0`）

## 为什么新增了「零产出锚点」这两条验收（2026-10-08 批次一实测补记）

原第 18–19 条验收测的是「**有没有对该锚点发出调用**」。而实际发生的失效模式是**调用了、但没有产出**——它从这两条验收的缝隙里穿过去。

**实测证据**（详见 [`docs/adr/ADR-015-reasoning-tier-decision.md`](../adr/ADR-015-reasoning-tier-decision.md) 的「发现一」）：

`chapter4` 的 20 个锚点中**每次运行都有锚点产出 0 个对象**，而且每次漏的**不是同一个**——**默认档与低档都一样**：

| 运行 | 档位 | 零产出锚点 | 该锚点是什么 |
|---|---|---|---|
| `run-7afb98d262b5`（旧提示词） | 默认 | 1 个：`h2-9` | 思考题 |
| `run-470138ece6a3` | 默认 | 1 个：`h2-9` | 思考题 |
| 批次一 默认#2 | 默认 | 1 个：`h2-8` | 本章小结 |
| 批次一 默认#3 | 默认 | 1 个：`h2-9` | 思考题 |
| 批次一 低档#2 | `low` | 1 个：`h2-8` | 本章小结 |
| 批次一 低档#3 | `low` | **2 个**：`h3-7`、`h2-9` | 多模态感知、思考题 |

`h2-8`（本章小结）在默认#1 与默认#3 里各产出 2 个对象，在默认#2 与低档#2 里**直接为空**；
`h2-9`（思考题）同样在 0 与 1 之间摆动。**这是同档位内部的摆动，不是档位效应**——
不要在这一点上做档位归因（ADR-015 记录了一次因此翻车的结论）。

而流水线对此**零信号**：回执全文提及该锚点仅 1 次（`perAnchor` 里的 `objectCount: 0`）；无任何 warning/note 字段；`reasonCodes` 只记了关于**已存在对象**的拒绝；`counts` 是 `{anchors:20, objects:34, passed:30, rejected:4}`——**「20 个锚点只产出了 19 个锚点的东西」这件事在计数里不出现**。

这正是 ADR-009 论证的现场验证（它当时是推理，现在是观测）：**少抽的对象根本不存在，没有任何判据会为缺席者报警。**

## 构建记录（2026-10-09）

### 一 · 第 9 条验收的措辞更正：**原文如此、实测为假、已改正**

第 9 条原文写的是「断言 9 个二级锚点**全部被覆盖到** —— 即没有整节被静默跳过」。**「被覆盖到」有歧义，两种读法给出相反结论**，而盘上 8 份真实回执给出的答案是：

| 读法 | 实测结论 | 是否成立 |
|---|---|---|
| 该锚点**被处理过**（发出了调用） | 8/8 次运行都是 20 个锚点全部被处理 | ✅ 成立 |
| 该锚点**产出了对象** | 8/8 次运行里都恰好有 1–2 个锚点为空，**且每次都不是同一个** | ❌ **不成立** |

零产出次数实测分布：`h2-9`（思考题）**6 次**、`h2-8`（本章小结）**2 次**、`h3-7`（多模态感知，305 字节）**1 次**。

**因此「9 个二级锚点全部有产出」这句话按第二种读法写进任何交付物都是错的。** 紧跟其后的第 21 条（「断言『已处理锚点数 = 索引中的锚点数』」）表明**原意是第一种读法**——「静默跳过」指没被处理。本轮的处置：

- 验收意图**不变**，第 21 条的机械判据照做，并硬实现为「整章跑完即断言 `perAnchor.length === anchorCount`，否则抛错」；
- 两件事在回执里**分开**：`coverage.processedAnchors`（被处理）与 `coverage.withoutObjects`（没被指向）；
- 第二种读法**不写成通过**——它是一种真实且每次都会发生的分布，必须被看见，所以它是固定字段。

完整推导与复算命令见 [`docs/adr/ADR-017-anchor-slicing-and-input-budget.md`](../adr/ADR-017-anchor-slicing-and-input-budget.md) 的「实测口径」二、三。

### 二 · 切分的层级：先按小节，再按段落

「按小节/主题边界切」在本流水线里是**两层**：

1. **小节边界**：第 1 层的锚点本身就是标题边界（`##` / `###` / `####`），每个锚点一次调用，
   因此**章节从不被按字节切开**——这一层在卡 04 就已成立。
2. **段落边界**（本轮新增）：**单个锚点自身**超出预算时，在该锚点内部按**空行且不在代码围栏内**切开。这不是新造一个切法，而是用 markdown 自身的段落结构。

刻意不做的两件事：**不按字节硬切**（会在句子中间断开）、**不在代码围栏内切**（会把一个代码块劈成两半，而代码块往往正是一段工程规则的唯一证据）。单个段落自身超预算时**整段交出并标 `oversized`**——宁可让这次调用超预算，也不切断它；这是唯一允许超预算的出口，且它进回执的 `layer2.splits`，**可见**。

**切分对第 3 层不可见**：`sourceRefs` 按**锚点**（不是切片）填入，因此每个对象依旧解析到同一个锚点、同一个 `lineStart`/`lineEnd`/`contentHash`。测试逐条与索引比对钉住这条性质。

### 三 · 预算是显式旋钮，缺省不触发

`DEFAULT_MAX_ANCHOR_BYTES = 24000`，可用 `--max-anchor-bytes` 覆盖。**这是选定的策略，不是测量结果**。

实测（复算命令见 ADR-017）：全书 13 份索引、**336 个锚点**，最大的是 `chapter10#h3-6` = **16,718 字节**；**超过 24,000 字节的锚点 0 个**。因此**缺省预算下全书没有任何锚点会被切分**，`layer2.splits` 是空数组——而「为空」本身就是一条可核对的结论：它说明这次运行的每个对象都来自一次看完整节的调用，而不是来自碎片。机制由构造出来的超预算锚点钉住，不靠真实语料偶然触发。

字节 → token 的换算取自实测拟合（chapter4 全部 20 个锚点）：`prompt_tokens = 1213.2 + 0.21175 × bytes`，残差 max|.| = 125.5 → **1 输入 token ≈ 4.72 字节正文**，另加约 1,213 token 固定开销。**这两个数不参与任何判据**（判据是字节数本身），只用来把预算翻译成人看得懂的 token 量级。

### 四 · 回执新增三个固定字段

| 字段 | 答的问题 |
|---|---|
| `coverage` | 索引锚点数 / **已处理**锚点数 / 有产出锚点数 / **零产出锚点清单** / 按层级分布 / 无法解析的出处锚点 |
| `counts.objectTypes` | 本章产出的类型分布，**九类全给（含 0）**——缺一个键与「这一类产出为 0」是两条不同的信息 |
| `layer2.usage` | 第 2 层按章的调用与 token，含逐锚点明细与**与客户端账本的对账** |

流水线版本从 5 升到 6：旧回执里**没有**这三个字段，而「字段缺席」与「该值为 0」语义完全不同（「零产出锚点 0 个」与「这份回执答不了这个问题」）。版本号进运行指纹，旧回执因此只能被当成旧口径的记录，不会被当成新口径的结论。

### 五 · 本轮修掉的缺陷

**测试抓到的真实缺陷：切分收尾少切一刀。** 收尾分支无条件 `spans.push([from, end0])`，没检查「从本片起点到锚点末尾」是否仍超预算。实测复现（预算 265 字节、六段正文、六处可用切点）：

```
修前：138 / 255 / 382   ← 最后一片比预算大 44%，而它明明还能再切一刀
修后：138 / 255 / 255 / 126
```

**它不会报错**——只会让这次调用更贵，并让**切分机制在它本该生效的地方悄悄失效**。测试里「非超大单段不得超预算」那条断言就是为它写的。

**重判路径丢掉逐锚点明细**（卡 07 点名的那个缺陷）：该路径原本只沿用账本，`perAnchor` 留在空数组上，于是「哪个锚点被处理过、哪个一个对象都没产出」在重判路径上**整体消失**。逐锚点明细是生产事实，与 `calls`/`tokens` 同类，已一并沿用。

**三处我自己的操作缺陷**：① 片校验最初写成 `index.lines ?? partial.lines ?? []`——索引根本不带 `lines`，退化成空数组后会把每个锚点都算成 1 片，从而**拒绝一切合法的片中断点**；② 片中断点校验最初「信 `partial.inFlight` 的字段」，改成用**同一个预算复算片数**再比对；③ CLI 上的措辞把「没有任何对象指向它」（替身/夹具路径）写成了「被处理但产出 0 个对象」——**字段名会撒谎**，已改为随 `processedKnown` 切换，并加测试钉住。

### 六 · 验了什么、没验什么

**验了**（321 项测试全绿，零网络、零凭据）：

- 切分只落在空行上、不在围栏内、行号是全文绝对行号、超大单段整段交出；
- 切分后所有对象逐条与索引比对 `anchor` / `lineStart` / `lineEnd` / `contentHash` 全部一致，且第 3 层独立复跑**零拒绝**；
- 整章覆盖 20/20、9 个二级锚点在注入传输下逐个核对；
- 零产出锚点进固定字段，且在**复用路径**与**重判路径**上都在；
- 类型分布九类全给且合计等于对象数；逐锚点用量求和 = 总量 = 客户端账本；
- 中断重跑不重复产出（id 无重复、总数正确、只跑剩下的锚点）；**片级续跑**（停在片中间时只补剩下的片）；
- 不可用的半成品（inFlight 指向的不是下一个锚点）被丢弃并写明原因。

**没验**：切分对**产出质量**的影响。缺省预算下全书没有锚点被切分，因此在本轮语料上**不可测**——详见 ADR-017 的「未决项」。
