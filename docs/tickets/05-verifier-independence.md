# 05：判定者的独立性（结构性隔离）

**要构建什么：**把第 3 层的判定者变成**结构上无法自评**的一步——它是一次独立调用，拥有自己的上下文与自己的实例标识，输入中只有主张、引文与对应锚点文本，拿不到生产者的推理过程、提示词与完整输出历史。

这一卡单独存在的理由：一旦判定者看得到生产者的上下文，它就会顺着生产者的说法同意，整个门禁变成橡皮图章。隔离必须写在代码里，写在文档里等于没写（方案 R4）。

### 隔离是构造的，不是删的

判定者输入**恰好三个键**（`claim` / `quote` / `anchorText`），由 `CLAIM_FIELDS` 逐类型列举主张字段。
刻意不用「传整个对象再删敏感字段」的写法：删除式隔离会被**将来新增的字段**默默绕过——
有人给对象加一个字段，判定者的视野就悄悄扩大了，而没有任何测试会失败。

守卫是**白名单**：多一个键即报错。黑名单（`FORBIDDEN_JUDGE_CONTEXT_KEYS`）只能拦住我们
想得到的泄漏，拦不住未知字段。缺键同样报错——判定者依据不足时会照样给出判定，
这类失败不会被它的输出暴露，因此必须在入口拦住。

### 隔离是被测试证明的，不是被声明的

`judge-isolation.test.mjs` 驱动**真实链路**（真实第 1 层索引 → 真实第 2 层物化 → 真实第 3 层验证），
用双替身传输把哨兵埋进三个必须不回流的位置，断言判定者**实际收到的请求**里一个都没有：

1. 生产者响应的**顶层字段**（对象数组之外）；
2. 对象上的**非主张字段**（`aliases`）；
3. 生产者响应的**原文尾部**（代表「完整输出历史」）。

提示词这一路用的是**派生哨兵**：生产者的 system 提示词由 `buildSystemPrompt()` 生成、是一个常量，
全链路没有注入点可以往里塞字面哨兵；因此把**生产者实际收到的整段 system 提示词**当作哨兵，
断言它不出现在判定者的任何请求里，并另用一条正向断言钉死判定者的 system 就是它自己的常量。
派生哨兵覆盖整段提示词，比字面哨兵更强。

**配了正向对照**：断言判定者确实收到了【主张】【引文】【锚点原文】三样、且请求正文超过 300 字。
没有这一条，「请求里没有哨兵」可能只是「请求是空的」——一个永远为真的测试等于没测。

### 调用实现不进 verifier

`verifier.mjs` 不 import `judgeObject`（判定者的调用实现），判定者由 `opts.judgeFn` 注入。
这条由源码级断言钉住（先剥注释再解析 import 绑定，避免把说明文字误判成代码）。
它存在的理由：仅断言「源码里没有 `fetch(`」是不够的——只要有人写一行 import，
本模块就重新获得了网络能力，而那条断言照样通过。

## ⚠️ 真实运行暴露的根本问题：`evidenceQuote` 被当了两个不同的用

**12 条「不充分」是同一个结构性模式，不是分散的偶发缺陷。** 判定者给的理由高度一致：

> 引文支持主张的**一部分**，但主张还断言了引文里没有的内容。

抽样核实（`CHAPTER4-H2-3-CONCEPT-01`）：主张说 MCP「是 Anthropic 于 2024 年底发布的开放标准…
采用客户端-服务器架构，并区分工具、资源与提示三类原语」，而它附的引文是
「一个 MCP 服务器可以同时被 Cursor、Claude Desktop、OpenClaw 等任何兼容的客户端使用…」。
**主张里的每一条断言都在锚点原文里**（实测逐句核对），只是**引文没选在支撑断言的那几段**。

### 根因：第 2 层的提示词把 `evidenceQuote` 定义成防编造凭证

实测第 2 层提示词原文：

> 「每个对象必须带 `evidenceQuote` 字段：从给定正文中**逐字复制**的一段文字（**不超过 120 字**）。
> 不得改写、不得拼接、不得翻译…第 3 层会把它与原文做**逐字比对**」

它回答的是「**模型有没有编**」，为此设了 120 字上限。而卡 05 的判定者问的是
「**这段引文是否支撑这条主张**」——同一个字段上的**第二个、不同的问题**，而该字段从未
为此被规定过。120 字上限使「引文覆盖一条综合主张」在多数情况下根本做不到。

**因此这不是第 2 层的执行缺陷，也不是模型不听话，而是卡 05 引入判定者时暴露的一条规格缺口。**

### 量化核查（实测，脚本口径：引文与各字段的二元组字符重叠率）

12 条中，引文最贴合的字段**不是**主张字段的有 **4 条**（引文实际支撑的是 `examples` /
`evidence` / `exceptions` 这类未进主张的字段）；其余 8 条引文与主张字段确有重叠但只覆盖一部分。

⇒ 这排除了「我的 `CLAIM_FIELDS` 选窄了」这一解释：把 `examples` / `exceptions` 也纳入主张
只会让主张**更大**，单条 120 字引文更难支撑，而不是更容易。

### 已定：`evidenceQuote` 同时承担两个用途（用户拍板，决策全文见 ADR-011）

拍板为「把『引文必须支撑主张』写进第 2 层提示词，并放宽字数上限」。三处落地：
提示词新增两条**耦合**要求（引文须承载主张的每一条断言 ＋ 主张不得断言引文之外的内容）、
契约描述写明两个用途、上限放提示词侧不进 schema。

**修复验证（`run-470138ece6a3`，判定者指纹不变、第 2 层指纹由 `prompt-f99d3ed8ead4`
变为 `prompt-22384598f992`，因此唯一变量是本次改动）：**

| | 修改前 | 修改后 |
|---|---|---|
| 通过 / 拒绝 | 25 / 12 | **32 / 2** |
| 拒绝率 | **32.4%** | **5.9%** |
| 引文长度（均值/中位数） | 60 / 51 字 | **169 / 150 字** |
| 主张长度（均值） | 58 字 | 61 字 |
| 主张 / 引文 长度比 | 0.96 | **0.36** |

修的是引文侧而非主张侧：主张长度几乎没变，引文近三倍。
代价是**单章两层输出 token 合计 +30.0%**（98,444 → 127,935），判定者一侧反而更省。

### 已定：`CLAIM_FIELDS` 纳入**范围限定类**字段（用户拍板，决策全文见 ADR-012）

拍板为「逐类型把范围限定类字段纳入主张」：`Metric.window` / `MentalModel.trigger` /
`Heuristic.trigger` / `EngineeringRule.appliesWhen` 四条纳入；`Case.context`、
`DecisionModel.inputs`、`Playbook.prerequisites` 与各类展开字段明确不纳入（逐条理由在 ADR-012）。

**验证（`--judge` 重扫同一批对象，只换「判定者看到的主张」，不重跑第 2 层）：**

| | 改动前 | 改动后 |
|---|---|---|
| 判定者调用 | 33 | 33 |
| 支撑 | 32 | **33** |
| 不充分 | **1** | **0** |

反证对象 `CHAPTER4-H4-2-HEURISTIC-02` 前后判定者理由：
「…而**主张未加该限定**，断言得更宽泛」→「引文明确说明**对于文本占主体的 PDF**…**直接支持该选择建议**」。
同一段引文、同一个对象——变的只是判定者能看到哪几个字段。

⚠️ **边界**：本章现在**零判定者类拒绝**，因此「全部通过」在这一个样本上**无法与橡皮图章区分**。
不得据此宣称判定者有效；本章能证明的只是它曾经抓出 12 条引文不承载主张的系统性问题。

### 已定：门禁完成度纳入 `runId`，两份回执并存（用户拍板，决策全文见 ADR-014）

`runId` 的指纹追加 `gate:{full|deterministic-only}`。理由与版本号进指纹同源：运行身份必须覆盖
「这次运行实际做了哪些事」；但门禁完成度是**每次运行各自的选择**而非流水线属性，故无法借版本号表达。

回放规则随之明确：**优先回放「做过判定者」的那份**，只在它不存在时才退回确定性-only 那份；
调用方显式要求判定者而只有确定性-only 那份时不回放。

**实测（本机，两份并存）：**

| 回执 | 门禁 | 通过/拒绝 | 判定者 |
|---|---|---|---|
| `run-ae23e8ac51f5` | `gate-1-full` | 33 / 1 | 已跑 33 次 |
| `run-c2deb413424d` | `gate-1-deterministic-only` | 33 / 1 | 未跑 |

不带任何开关重跑 → 回放的是 **full** 那份（`run-ae23e8ac51f5`），验证了「优先取更完备的记录」。

**一次性代价（已付）**：现行回执的 id 不含门禁，故在新规则下全部失效。收敛路径实测为
「一次普通运行（**0 次模型调用**）写出门禁为 deterministic-only 的新回执」；
若要把「做过判定者」的那份也重建，需传 `--judge`（本章 33 次判定调用，实际付了）。
旧回执原样留在 registry 里——它们是历次运行的事实，只是不再被按 id 查到。

### 已定：提示词漂移**告警后复用**，不硬拒（用户拍板，决策全文见 ADR-013）

复用前比对产出者指纹与当前提示词指纹；不一致则 stderr 告警（并排列出两个指纹 + 给出 `--rerun` 出路），
并把观察结果记入 `reuseObservation`。**不硬拒**的理由是「提示词变了」与「源版本变了」性质不同：
源变了对象**失效**，提示词变了对象**仍然有效、只是旧了**。

一处明确接受的边界：**纯回放路径不写盘**（盘上那份回执是产出者的记录，内容不该随「谁读了一遍」而变），
因此漂移观察只出现在 stderr 与 `--json` 输出里，**审计平面上看不到**。让它在盘面上可见需要先给
运行身份定清楚（即待定一），因此不顺手改。

### 一处关于三值语义的实测特性：真实数据上只出现两个值

12 条拒绝**全部是「不充分」，「不支撑」一条都没有**。这不是巧合，而是当前设计下的结构性倾向：

`evidenceQuote` 必须**逐字命中它自己的锚点区间**（确定性判据强制），而该对象的主张也是从
**同一个锚点**归纳出来的。因此引文与主张**在话题上几乎必然相关**——「完全不相关」的引文
要模型在自己刚读过的那段正文里刻意挑一句无关的话才会出现。
于是「引文相关但不足以承载主张」成了主要的失败形态，而「引文与主张无关或相矛盾」很少发生。

**这条特性有两面，都要如实记下：**

- 正面：`JUDGE_INSUFFICIENT` 与 `JUDGE_NOT_SUPPORTED` 分码并非纸面设计——前者在真实数据上
  确实是主要形态，而它的修复方（锚点切分 / 主张写宽）与后者（重选引文）确实不同。
- 负面：「不支撑」这条路径**在真实数据上从未被触发过**，因此它的语义与判据目前的证据
  只来自离线 fixture。**不得**据此宣称三值判定已被真实验证——被真实验证的只有两值。

## 验证过程中抓出的两个缺陷（都不是判定者的问题）

这两个都是在「用真实 CLI 验证本卡功能」时抓到的，**离线测试当时全绿**——因为它们都落在
测试没有覆盖的那一层。

### 缺陷一：CLI 收下参数然后默默丢掉

`main()` 此前**逐个枚举**要传给 `runPipeline` 的字段（`layer2:` / `rerun:` / `llmModel:` …）。
本卡给判定者新增了六个开关，参数解析加了，这份清单忘了加——于是 `--judge` 看起来被接受、
实际什么都没发生。实测踩到：一次重扫跑了 **0 次模型调用**，而输出照常显示「通过 33 / 拒绝 1」。

**离线测试为什么没抓到**：它们都直接调 `runPipeline()`，**绕过了 CLI 这一层**。

**修法不是补那六行**（下次加参数照样会忘），而是：

1. 新增 `buildRunInput(flags, {target, repoRoot})`，改成**整体透传** `...flags`，
   只保留三处**穷尽列举**的有意改写（`source` 位置参数落字段、`repoRoot` realpath 归一、
   `objectsFixture` 空串归 null）；
2. 新增 `pipeline/tools/test/cli-flags.test.mjs` 钉住那条被违反的**性质**：
   `parseArgs` 产出的每一个键都必须原样出现在入参里，且**清单之外不得有任何改写**。
   这条成立时，将来任何人新增参数都不可能再犯同一个错——因为没有任何清单要维护。

### 缺陷二：一份没扫过判定者的回执会挡住 `--judge`

回放判据此前只看「版本 + 对象」。于是「先用 `--no-judge` 跑过、再用 `--judge` 重扫」这个
正常操作序列里，第二会被原样返回第一份**只跑了确定性判据**的回执——用户拿到
「通过 33 / 拒绝 1」，而他要的判定者从未运行。

**显式指令被吞掉比报错更糟：它看起来成功了。** 这也是本卡反复强调的同一种失败模式。

已修：回放前比对**门禁完成度**——要重扫判定者，就不能拿一份没扫过判定者的回执交差。
反向对照（完成度一致时仍然回放）也有测试钉住，免得把整条回放路径废掉。

### 附带暴露：门禁不同的两份回执**无法并存** → 已由 ADR-014 解决

修完缺陷二之后，测试立刻抓到第三个后果：同一批对象、同一版本下两次运行的 `runId` **相同**
（当时的 `runId` 不含门禁完成度），所以「deterministic-only」那份会被「gate-1-full」那份**覆盖**。

**而且被覆盖的不是子集**：确定性-only 判它通过的，全覆盖可能判它不通过，两份的 `counts` 不同。
即「同一批对象在两组判据下各自的结论」这本该并存的记录，丢了一份。

**中间处置（保留在本记录里）**：先让它**不静默**——覆盖时在 stderr 上指名道姓地说出被覆盖的是
哪一份、并说明它不是本次的子集；测试同时钉住「确实只有一份」与「覆盖被说出来了」。
这一步先做、且**没有跳过**，是刻意的：在根本解法落地之前，一个已知会丢记录的路径**不得是静默的**。

**根本解法已落**（ADR-014）：门禁完成度纳入 `runId`，两份各有其名、并存。
测试随之从「只有一份」改为「两份并存且门禁各一」，并新增 `stderr` 里的并存说明断言。
