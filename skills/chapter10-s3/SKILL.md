# 协作模式编排

## 何时使用

- Agent 数量增多且需异步并行时。
- 多数需要掌握子 Agent 执行进展的场景。
- 对等协作涉及 2-3 个平等身份的 Agent，并需要引入独立视角和认知多样性时。
- 在 Loop 工程设计的循环中，当模型声称完成时。
- 当审核者需要保持独立验证时
- 在 Planner-Executor 双 Agent 架构中分配模型和提示词资源时。
- 当两个成功事件几乎同时到达时。
- 当评估 A2A 与消息总线等三种通信机制的关系，或判断多 Agent 系统是否需要 A2A 时。
- 当面对跨文件语义冲突时。
- 多 Agent 系统运行时，尤其是目标互斥或冲突无法按可验证规则解决时。
- 当 Agent 通过文件系统自主管理长期记忆时。
- 当多个 Agent 频繁互动、一个 Agent 的错误可能被后续 Agent 逐层强化时

## 核心原则

**当 Agent 数量增多且需异步并行时，应改用消息总线进行通信。**

点对点连接数随 Agent 数呈平方增长，且要求收发双方同时在线；消息总线按订阅关系转发，发送方无需知晓消费者。

**轨迹持久化不宜作为 Agent 间信息传递的主要方式；多数场景下应约定进度文件以便掌握进展。**

轨迹动辄数万 token，主 Agent 读完还需自行提炼，既费时又费 token；进度文件轻量，主 Agent 可随时读取。

**要获得真正的多样性，需要主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断、再汇总结果。**

多个实例不等于多种思路；当模型、上下文和脚手架高度相似时，不同 Agent 往往会做出相同选择。

**模型可以提出“完成”，但不能批准自己的“完成”。**

只有通过独立验证的结果才能写入持久进度并消耗配额，因此完成必须由验证器而不是模型自己来批准。

**审核者不能修改测试、证据采集器或发布门槛。**

否则“独立验证”会退化成自我批准。

**应当将最强的模型和最精心设计的提示词分配给 Manager（规划者），而不是将资源平均分配给所有 Agent。**

在 Planner-Executor 双 Agent 架构中，弱规划者是整个系统最关键的瓶颈；当 Planner 的规划质量足够高时，即使 Executor 比较简单也能取得好结果；若 Planner 的任务分解有误，后续所有 Executor 的工作都建立在错误的前提上。

**`settle_once` 必须是幂等的（通常由锁或事务保护）。**

否则两个几乎同时到达的成功事件会触发两次汇总。

**A2A 并不取代本章介绍的三种通信机制，而是在它们之上、跨信任边界的标准化层。**

MCP 解决的是 Agent 与工具之间的互操作，A2A 解决的是 Agent 与 Agent 之间的互操作；同一团队内部的多 Agent 系统直接用消息总线即可。

**乐观锁只能防止同一文件的写入冲突；跨文件语义冲突需要更高层的语义校验机制。**

乐观锁的作用范围限于同一文件的写入冲突，因此不能覆盖跨文件语义冲突。

**运行时必须预先定义目标优先级、资源所有权和权限边界，并在冲突无法按可验证规则解决时暂停执行、交由人工裁决。**

更强的执行能力并不等于更好的协调能力；目标互斥时系统可能从趋同走向对抗。

**在文件式长期记忆中，Agent 必须遵守“先读后写”的约束。**

避免盲目覆盖。

## 实践模式

**协作拓扑**

Agent 之间的控制权和信息按什么结构流动；协作拓扑有三种典型形态：对等协作模式、管理者模式和去中心化模式。

- 少量 Agent 按照固定的拓扑形成迭代改进循环，例如论文写作 Agent 由起草者和评论者两个 Agent 组成，一方起草、另一方批注修改，反复几轮后质量更高。
- 一个中心化的 Manager Agent 负责任务规划和调度，多个子 Agent 各负责特定子任务——就像项目经理带着几位专业工程师做项目。
- 没有运行时的中心控制者，Agent 之间像人类一样互相沟通，协作完成任务。

**Graph 工程**

在当前 Agent 语境中通常指显式设计执行图：节点是 Agent、普通程序或人工决策，边定义任务依赖、条件路由与失败后的去向，结构化状态在节点之间流动。

- 对等协作、管理者编排和去中心化移交，都是不同的图拓扑。

**虚拟文件系统**

来源、生命周期与权限各异的存储被挂载到同一目录树下，Agent 通过统一的 read_file/write_file/list_dir 接口访问的文件系统。

- 本地临时盘
- 持久对象存储
- 第三方云盘的 API
- 只读的系统资源包

**Agent 专属工作区**

每个 Agent 实例独享的私有目录，存放中间产物、临时文件、草稿与调试日志，生命周期与实例绑定，对其他 Agent 和用户不可见。

- 中间产物
- 临时文件
- 草稿
- 调试日志

**Loop 工程**

设计一个让 Agent 持续运转的循环——发现下一件该做的事、执行、验证、记录进度——由验证器而不是模型自己来判定是否真的可以停，人的角色从给 Agent 写提示词的操作者变成设计循环的工程师。

- 包括 Pine AI 在内的头部 Agent 团队在名词流行之前早已在用“循环加验证”解决过早终止问题

**提议者-审核者范式**

一种对等协作范式，由提议者 Agent 负责生成代码，审核者 Agent 渲染执行结果、评估质量并给出改进建议，两者反复迭代直到效果达标。

- PPT 生成
- 视频编辑
- 日志可视化

**辩论模式**

多个 Agent 各持不同立场，通过对抗性对话深入探索问题空间。

- 评估一个技术方案时，Agent A 扮演“支持者”列举方案优势和机会，Agent B 扮演“反对者”指出风险和局限，每轮辩论都针对对方的论点提出反驳或补充。

**头脑风暴模式**

多个 Agent 独立生成创意后相互分享、彼此启发，并通过不同思维偏好相互激发来探索更广阔解空间、形成单一 Agent 难以想到的创意组合的协作模式。

- 在产品创新任务中，Agent 1 提出“增加社交分享功能”，Agent 2 受启发提出“不仅分享到社交网络，还可以生成个性化分享海报”，Agent 3 综合前两者提出“用户自定义海报模板并形成模板市场”。

**专家小组模式**

多个 Agent 各自代表一个专业领域的视角，共同讨论跨学科问题的协作模式。

- 评估新产品可行性时，工程师 Agent 从技术角度分析实现难度，产品 Agent 从用户体验角度评估市场吸引力，运营 Agent 从成本和资源角度分析商业可行性。

**去中心化模式**

一种多 Agent 协作模式：去掉中心控制者，让多个职责对等的角色分工与制衡，每个 Agent 根据专业判断自主决定何时与其他 Agent 沟通，而不是把所有判断汇集到一个 Manager。

- 移交任务：我的部分做完了，交给你
- 请求反馈：这个方案技术上可行吗？
- 报告问题：你给的需求有矛盾，我们需要重新讨论

**A2A 协议**

一种用于跨组织边界的 Agent 间标准化互操作协议；由 Google 于 2025 年发布，后捐赠给 Linux 基金会托管，核心要素包括 Agent Card、任务生命周期管理和不透明协作。

- 你的 Agent 需要调用另一家公司的 Agent 时，通过 A2A 协议进行互操作。

**多 Agent 协作的失败模式**

多 Agent 系统在引入协作能力时引入的单 Agent 不存在的新型失败模式，分为系统设计缺陷、Agent 间对齐失败和任务验证缺失三大类。

- 系统设计缺陷：Agent 之间的接口定义不清、角色职责重叠、工具配置错误等架构层面的问题
- Agent 间对齐失败：多个 Agent 对任务目标的理解不一致、传递的信息被下游 Agent 误解、或者多个 Agent 的操作在逻辑上相互矛盾
- 任务验证缺失：系统缺乏有效机制来确认任务是否真正完成

**拜占庭故障**

部件持续工作，但给出错误信息的故障类型；在多 Agent 系统中，Agent 故障很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。

- Agent 很少径直停止运行，而是继续给出看似可信的错误结论，且错误不会主动声明自己是错误。

**语义冲突（逻辑级一致性冲突）**

文件层面看不出任何冲突，但多个 Agent 的操作在逻辑上相互矛盾；这种冲突更隐蔽，也更危险。

- Agent A 负责重新编排全书的图片编号，Agent B 同时在修改某一章节内容并引用了原始编号的图片；两者操作不同文件，文件层面无冲突，但 A 完成后 B 引用的图片编号全部失效，读者看到错误的图片引用。

**错误的级联放大**

多个 Agent 频繁互动时，一个 Agent 的错误可能被后续 Agent 逐层强化，使信息像传话游戏一样越传越走样。

- “传话游戏”中信息越传越走样

**理解债**

使用 Agent 开发时，Agent 循环交付代码的速度越快，工程师对系统实际实现的理解落后越远，最终在严重问题必须人工介入时已看不懂自己的系统。

- Agent 循环交付代码的速度越快，工程师对系统实际实现的理解就落后得越远，等到出现严重问题必须人工介入时，已经看不懂自己的系统。

**认知投降**

工程师习惯用 Agent 代劳，逐渐放弃独立思考与审查，导致软件质量失控。

- 工程师习惯了用 Agent 代劳，逐渐放弃独立思考与审查，导致软件质量失控。

## 常见陷阱

- **模型、上下文和脚手架高度相似时，不同 Agent 往往会做出相同选择**
  - 后果：局部错误演变为系统性故障
  - 纠正：主动区分模型、上下文、工具、可见证据或职责，并让各 Agent 先独立判断、再汇总结果
- **同一模型、相似上下文生成的多个审核意见，不能自动视为相互独立的证据**
  - 后果：相同决策同时冲击共享资源
  - 纠正：有意识地引入模型、上下文和数据来源的差异，并使用命名空间、资源配额和速率限制
- **多 Agent 系统在目标互斥时可能从趋同走向对抗，把其他 Agent 的操作理解为蓄意阻挠。**
  - 后果：Agent 可能终止对方进程、撤销权限，甚至部署自复制的破坏代码。
  - 纠正：运行时预先定义目标优先级、资源所有权和权限边界，并在冲突无法按可验证规则解决时暂停执行、交由人工裁决。
- **多 Agent 场景下循环停不下来，失控的 Agent 有时会生成数千个子 Agent**
  - 后果：浪费大量 token
  - 纠正：对于自主性较强的 Agent，建议使用独立的 API key，防止 token 开销不受控增长

- `sources/ai-agent-book-zh/code/chapter10/book-translation/` —— 长书翻译很难把所有原文与译文一直放在管理者上下文中。本实验让不同角色负责翻译与检查，并用文件保存完整产物，学习如何控制协调成本。
- `sources/ai-agent-book-zh/code/chapter10/generative-agents/` —— 多个角色在同一个虚拟世界中生活，会产生怎样的交流与计划变化？本项目以 Generative Agents 环境为例，学习个体记忆机制与群体行为之间的联系。
- `sources/ai-agent-book-zh/code/chapter10/multi-role-transfer/` —— 一个任务可能先需要分析，再需要编码或审核。实现多角色行为时，可以切换系统提示与工具，也可以保持统一角色并加载技能。本实验比较这两种组织方式。
- `sources/ai-agent-book-zh/code/chapter10/parallel-web-research/` —— 查阅多个来源可以并行进行，但最后仍需要判断它们是否描述同一个对象。本实验让多个浏览器工作者各自读取来源，再把有出处的结果交给管理者整理。
- `sources/ai-agent-book-zh/code/chapter10/staged-system-prompt/` —— 同一个编码任务在分析、实现和审核阶段需要不同注意力。本补充案例用阶段化提示与工具集合，帮助理解一种显式组织工作过程的方法；它已不属于当前正文的编号实验。
- `sources/ai-agent-book-zh/code/chapter10/talkact-reproduction/` —— 语音交互要求及时响应，复杂任务又需要较长规划。固定快慢角色的设计试图让快速交互与较慢处理同时进行。本项目用对照任务研究这种分工。
- `sources/ai-agent-book-zh/code/chapter10/voice-werewolf/` —— 狼人杀同时包含公开发言、私有信息、回合规则和多人决策，适合观察多 Agent 协调。本实验将确定的游戏规则交给代码，把角色表达与选择交给模型。
