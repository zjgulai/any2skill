# 从失败轨迹生成可回滚指令补丁

## 何时使用

- 某类失败反复出现、需要把教训固化进指令或文档时
- 修订 Agent 的提示词、技能文档或操作手册时
- 决定一条知识应以文档、可执行程序还是参数形式承载时
- 外部内容可能进入长期记忆/经验库、需要审查写入路径时

## 输入与前置条件

- 失败轨迹与证据（发生了什么、影响是什么）
- 现有指令/文档/程序的载体现状
- 修订范围约束（哪些载体可改、谁能批准）

## 执行步骤

1. 收集失败轨迹并归类，确认是偶发还是模式；只有可复现的模式才值得修订。
2. 选择载体：按知识「表示的性质」决定写文档、写程序还是进参数；稳定但频繁变更的内容提高更新频率而不是换载体。
3. 生成最小 diff：修补必须带来源（哪条轨迹、哪条证据），禁止整份重写提示词或文档。
4. 审查写入路径：外部内容与第三方摘要不得未经审查进入长期记忆或经验库，防止一次性攻击跨会话潜伏。
5. 对补丁做验证：在相关场景上复跑或人工复核，确认修复成立且无副作用。
6. 记录补丁版本与回滚点。

## 交付物

- 带来源的最小 diff 补丁
- 载体选择说明
- 验证记录与回滚点

## 检查、停止与回滚

- 每个补丁都能追溯到具体失败轨迹或证据
- 没有整份重写；diff 是最小集
- 长期记忆/经验库的写入全部经过审查路径，无外部内容直写
- 补丁在相关场景上有验证记录
- 停止条件：失败无法复现或归类不清时，先补证据再修订
- 停止条件：修订涉及权限边界或安全规则变更时，转安全评审流程
- 回滚：已定义。保留上一版载体内容；回滚即恢复上一版并复跑验证场景。

## 依据与边界

**来源规则**

- 当你在模型之上造应用时——建议：将 harness 作为短期最锋利的杠杆争取时间，同时构筑技术之外的护城河：独占数据、稳固渠道、用户信任、网络效应、人与 Agent 协作的物理世界场景。
- 当更新部分是事实：进入知识库；当更新部分是解释例外的原则：进入 Skill；当更新部分是不可绕过的权限：由程序门控；当更新部分是高维识别能力：进入参数
- 修改应是带来源的最小 diff，而不是让模型每次都重写整份 Prompt。
- 是否将某项能力参数化，并不由任务是否长期稳定单独决定；真正决定主要载体的是能力的表示性质，稳定性只影响更新频率和成本。
- 对持续进化而言，应把经过评价的生产轨迹转化为训练数据：高质量示范进入 SFT，明确偏好形成成对数据，具有可靠环境奖励的交互用于 RL。
- 自动课程、可执行技能和环境验证缺一不可

**来源陷阱**

- 反复让模型重写整份 Prompt 或记忆
  - 后果：旧版本中的少数重要细节可能在多轮改写后逐渐消失；相互制约的条件也可能被合并成一句过度抽象的原则。
  - 纠正：Agentic Context Engineering（ACE）把上下文维护成带稳定标识符的条目集合，由生成、反思和整理模块提出增量更新，再用确定性逻辑合并与去重，而不是每轮重写一个越来越短的文本块。
- 让外部内容或提示注入未经审查地写入 Agent 的长期记忆/经验，使一次性攻击跨会话潜伏并反复生效。
  - 后果：攻击者可将偏见或恶意指令潜伏在长期记忆中，在后续会话中触发，导致持久威胁，扩大攻击影响。
  - 纠正：写入长期记忆的内容必须经过与外部内容同等的信任审查，避免恶意指令潜伏；对自我进化系统，将提示注入总结为经验前需验证来源并隔离。

**适用边界**

- 不是完整的训练/微调管线：不覆盖数据标注与参数训练
- 不覆盖模型选择或推理参数调优
- 不代替代码评审流程，只负责经验到指令的转化与验证
